# 攻城略地逐回合日志 v1

日志由公开材料的 `arena.py` 和评分端 `tournament.py` 共用裁判产生。每局独立一个 UTF-8、无 BOM 的 `.jsonl` 文件，每行一个完整 JSON 对象，依次是一个 `header`、若干 `turn`、一个 `result`。行以 LF 结束。数组有稳定顺序；对象字段顺序没有语义。兵力、坐标、回合、节点编号、命令字段均为整数，毫秒和换算系数可以是小数，计时值只是实测数据，不参与播放器插值。

播放器只需要日志文件，无须程序、仓库、地图生成器或引擎。按 `initial_state` 展示初始局面，按每条 `turn` 的事件播放，再以其 `state` 对齐精确局面。

## 归属、节点、部队和局面

整个日志固定使用甲方视角：`owner=0` 是中立，`1` 是甲方，`2` 是乙方。节点编号对双方一致，不能对换编号或坐标。乙方选手收到的局面内部会交换归属 1/2，但日志里的命令、状态和事件都已使用上述绝对视角。

节点对象为 `{"x":8,"y":0,"owner":1,"troops":100,"growth":5}`。`nodes` 数组下标就是节点编号。坐标固定，节点以原点为中心、每两个成对对称；显示时可把 y 轴向上。

部队对象为 `{"owner":1,"troops":50,"from":0,"to":2,"turns_left":3,"total_distance":5,"id":"t1-p1-o0"}`。`from/to` 为节点编号，`turns_left` 是剩余路程，`total_distance` 是起终点间固定的总路程（整数向上取整直线距离）。出发、在途状态、到达事件里的部队对象均带总路程。`id` 整局唯一，形如 `t<出发回合>-p<绝对归属>-o<命令的零起始下标>`。初始部队数组为空。早期 v1 日志没有 `total_distance` 时，播放器按地图起终点坐标计算即可；这是兼容新增字段，不改变版本号。

局面对象为 `{"turn":1,"max_turns":200,"nodes":[...],"fleets":[...]}`。`turn` 表示即将执行的回合。第 t 回合结算后的局面 `turn=t+1`，因此打满 200 回合后为 201。`fleets` 只含尚未到达的部队，顺序是原在途部队后接本回合新出发部队，并移除已到达者；不同部队不会合并。

直线路程为 `ceil(sqrt((x1-x2)^2+(y1-y2)^2))`。出发回合已经推进一次：第 t 回合出发、总路程 d 的部队在第 t+d-1 回合的到达阶段到达。回合开始时剩余路程 k 的部队，在该回合起第 k 个回合（当前回合算第 1 个）到达。动画可用 `(d-turns_left)/d` 作为回合开始时的路程比例。

## header

字段如下：

| 字段 | 含义 |
|---|---|
| `type` | 固定为 `header` |
| `schema` | 固定为 `siege-replay-v1`，未来不兼容变更会换版本 |
| `seed`、`map_generator` | 地图整数种子、生成器版本 `siege-map-v1` |
| `name` | 调用者可选的比赛名称，默认空串 |
| `players` | 两个对象，按甲/乙顺序；`seat` 为 1/2，`label` 为机器使用的身份键，`display_name` 为可读显示名（如模型名、第几档对手），`executable` 为运行路径，`cpu` 为逻辑处理器编号，`cycles_per_ms` 为本局固定使用的实测系数。早期日志没有显示名时使用 label。公开 CLI 可用 `--name-a`、`--name-b` 设置，默认可执行文件名；正式 Match 可传 `display_names=("模型名","第2档")`，未提供时回退到 labels |
| `rules` | `max_turns=200`、`first_cpu_ms=1000`、`cpu_ms=50`、`wall_ms=5000`、`memory_bytes=1073741824`、`command_limit=1000`。开发选项 `cpu_time_scale` 会乘 CPU 预算，默认 1；墙钟及内存上限不随之变化。正式使用 1。`simultaneous_forfeit=draw` 表示同回合双方判负时记平局（待题面负责人确认） |
| `initial_state` | 完整初始局面，含地图、兵力、增长率和空的在途部队数组 |

## turn：命令与计时

每个 `turn` 对象的 `turn` 是本次尝试执行的回合号。`players` 数组仍按甲/乙顺序，其中每项包含：

| 字段 | 含义 |
|---|---|
| `commands` | 实际收到的完整命令列表，每条为 `[from,to,troops]`，保持返回顺序，包括无效命令和第 1001 条以后的命令。若程序尚未交出完整响应就终止，该数组为空；不完整字节流不算交出的命令 |
| `applied` | 交给引擎检查的完整列表。CPU 超时或该方判负时为空，否则等于 `commands`。这里的“交给引擎”不表示命令有效 |
| `discard_all` | `null` 表示没有整回合作废；`cpu_timeout` 表示 CPU 超时整回合作废，否则是该方的判负原因 |
| `timing` | 下表的计时与判罚数据 |

`timing` 字段：

| 字段 | 含义 |
|---|---|
| `cpu_cycles` | `QueryProcessCycleTime` 的累计进程周期计数，含用户态和内核态 |
| `delta_cycles` | 本次计费周期增量。首回合从 0 起，包括进程启动、全局初始化；后续回合以上一次完整交令时读到的累计数为基点，回合间偷算也计费 |
| `cpu_ms` | `delta_cycles / header.players[i].cycles_per_ms` |
| `wall_ms` | 该回合发局面到完整交令（或发现失败）的墙钟时间，首回合也从本方局面发出时开始。创建进程的系统等待不计入交令墙钟；首回合 CPU 仍从周期计数0起，包括全部启动和全局初始化 |
| `process_setup_wall_ms` | 仅首回合有：从请求创建本方进程到向其发送首个局面的准备墙钟时间，不计入交令5秒截止，用于定位系统加载/启动慢问题 |
| `process_creation_wall_ms` | 仅首回合有：Windows CreateProcess 返回前的准备墙钟时间，是上项的一部分 |
| `nominal_budget_ms` | 首回合 1000，其余 50；开发可乘 `cpu_time_scale` |
| `debt_before_ms`、`available_ms`、`debt_after_ms` | 原有欠时、`max(0,预算-原欠时)`、`max(0,原欠时+本次用时-预算)` |
| `cpu_timeout` | 当 `原欠时+本次用时>预算` 为 true，本回合全部命令作废。欠时用以后回合预算抵扣，不抹零 |
| `consecutive_timeouts` | 连续 CPU 超时回合数，正常回合归零，达到 3 判负 |
| `failure` | `null` 或 `three_cpu_timeouts`、`wall_timeout`、`process_exit`、`memory_limit`、`protocol_error` |
| `exit_code` | 当时系统可见的进程退出码；尚未退出为 `null` |
| `memory_limit_bytes` | 固定为 1073741824，通过 Windows Job Object 的每进程提交内存硬上限实现 |
| `detail` | 可选，异常/协议失败的说明文本 |

CPU 超时后，裁判仍读取本回合带回合号的响应（最多等至该回合 5 秒墙钟截止），将整份响应丢弃，才发送下一回合局面；因此晚到命令不会串进下一回合。等待本身不消耗该选手 CPU。若 5 秒仍未收到完整响应则直接判负。双方先拿到同一个回合开始局面，裁判收到双方结果后才结算。

每方进程完成创建、绑核和恢复后立即发送首个局面，无须等待另一方创建完成。读线程在收到完整响应时记录完成时间；另一方 CreateProcess 很慢也不会让已经及时交出的命令被误记成墙钟超时。确实在收到局面后睡眠超过5秒仍判负。

`protocol_error` 针对不是官方 `main.cpp` 所产生的损坏通信（例如输出垃圾、错回合号）。官方 `decide()` 返回的非法节点、负兵力等正常进入引擎并逐条丢弃，不会触发协议判负。

## turn：结算事件和结算后局面

`settled=true` 的回合严格按出发、推进及增长、到达三阶段播放。以下事件都可直接读取，无须播放器再实现裁判：

1. `orders`：甲方列表在先、乙方在后，各自保持原顺序。每项为 `{"owner":1,"index":0,"order":[0,2,50],"reason":"accepted","fleet_id":"t1-p1-o0"}`。`index` 从 0 起，`fleet_id` 在丢弃时为 `null`。`reason` 枚举见下表。只含 `applied` 里交给引擎的命令；被 CPU 超时整回合作废的列表保留在 `players[].commands`，不出现在这里。
2. `departures`：有效命令产生的部队，含上述唯一 `id`，`turns_left` 此时等于总路程 d，还未推进。从源节点扣除对应兵力。出发可以清空节点，归属仍保留。列表按有效命令处理顺序排列。
3. `movement`：本次全部在途及新出发部队各一项，形如 `{"id":"...","before":3,"after":2,"arrived":false}`，表示剩余路程统一减 1。`after=0` 的部队在此回合到达，`arrived=true`。
4. `growth`：每个原本非中立的节点一项，形如 `{"node":0,"owner":1,"troops_added":5}`。在所有出发扣兵之后增长，在到达结算之前增长，中立不增长。
5. `arrivals`：按目标节点编号升序，每个有到达部队的节点一项，具体字段见下文。
6. `state`：本回合结算完成后的完整局面。所有到达部队从在途数组移除，节点归属和兵力已经更新。动画末尾以此为准。

命令 `reason`：

| 值 | 含义 |
|---|---|
| `accepted` | 有效，生成部队 |
| `command_limit` | 该方第 1001 条及以后的命令；先按此条件丢弃 |
| `invalid_node` | `from` 或 `to` 越界 |
| `not_owned` | 出发节点不属于下令方 |
| `same_node` | 起终点相同 |
| `nonpositive` | 派兵数不大于 0 |
| `insufficient` | 派兵数超过处理到这条时源节点剩余兵力；整条丢弃，不截断 |

一条命令若同时违反多个条件，按上表的顺序记录第一个原因。列表前面的有效命令已经扣兵，后面的命令以扣兵后的数量判断。

到达对象示例（3 方兵力中 30 最大、20 次大，所以甲占有并剩 10）：

```json
{"node":2,"old_owner":0,"old_troops":10,"sums":[10,30,20],"participates":[true,true,true],"fleets":[{"id":"t4-p1-o0","owner":1,"troops":30,"from":0,"to":2,"turns_left":0},{"id":"t3-p2-o1","owner":2,"troops":20,"from":1,"to":2,"turns_left":0}],"owner":1,"troops":10,"tie":false}
```

`old_owner` 是到达前、增长后的节点归属，`old_troops` 是出发已扣兵且增长已加兵后的兵力。`sums` 和 `participates` 是长度 3 的数组，下标分别为中立、甲、乙。原归属即使兵力为 0 也参加。`fleets` 是此次到达的完整部队列表，剩余路程均为 0。`owner/troops` 为结算结果。最大兵力唯一时，最大减第二大；只有一方时就是该方兵力。最大两方相等时 `tie=true`，节点归属保留 `old_owner`、兵力为 0，即使旧归属不在并列两方中也保留。三方兵力不能按两两对打或依次相减。

`settled=false` 表示本回合因判负终止，尚未发生出发、增长、推进、到达；上述事件数组全为空，`state` 为上回合结算后的局面（首回合则为初始局面），所以该条 `state.turn` 等于本条 `turn`。此时即使另一方有及时交出的命令，也不再执行。

## result

| 字段 | 含义 |
|---|---|
| `type` | 固定 `result` |
| `seed`、`name`、`labels` | 同本局元信息，`labels` 仍按甲/乙顺序 |
| `display_names` | 按甲/乙顺序的可读名称，早期日志没有时使用 labels |
| `winner` | 1 甲胜、2 乙胜、3 平；终局不出现 0 |
| `winner_label` | 获胜程序的身份标签，平局为 `null` |
| `score` | 按甲/乙顺序 `[1,0]`、`[0,1]` 或 `[0.5,0.5]` |
| `reason` | `elimination`（消灭）、`turn_limit`（200 回合比总兵力）或 `forfeit`（判罚终止） |
| `turns` | 已完成结算的回合数，因判负终止的未结算回合不算 |
| `failure_turn` | 判罚发生的回合号，否则 `null` |
| `totals` | 甲/乙总兵力；各自节点兵力加各自在途兵力，中立兵力不计 |
| `max_turn_cpu_ms` | 甲/乙逐回合实测 CPU 用时最大值，含首回合和判罚回合，不是加上欠时后的值 |
| `cpu_timeouts` | 甲/乙 CPU 超时回合数，包含最终判负回合 |
| `forfeits` | 甲/乙判负原因；无判负位置为 `null` |
| `cpus` | 甲/乙各自绑定的逻辑处理器编号 |
| `log` | 日志绝对路径；播放器无需使用该路径 |

消灭的定义是既没有归属节点，也没有在途部队；0 兵力的有主节点仍然存活。满 200 回合后先检查消灭，再比较总兵力；相等平局。双方同回合都触发判罚目前按平局处理，两侧原因都保留。

没有 `result` 结尾的文件表示工具异常中断或用户停止，可以播放已有完整行，但不能视为一局已完成对局。裁判自身或环境故障会向调用者抛异常，不伪装成选手判负。
