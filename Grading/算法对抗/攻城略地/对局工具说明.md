# 正式对局工具

`judge_core.py` 载入公开目录中原样的 `referee_core.py`、`winproc.py`，结算桥接原样包含公开 `engine.hpp`。公开 `arena.py` 与正式 `tournament.py` 共享这一份裁判、计时、判罚和日志代码。不要另写 Python 版本的 `step`。

未来 `evaluate.py` 可直接调用：

```python
from judge_core import Match, run_matches

matches = [Match(seed=seed, a=submission_exe, b=opponent_exe, labels=("submission", "tier1"))]
games = run_matches(
    matches,
    cpus=list(range(16)), jobs=8,
    build_dir=work_dir / "build",
    calibration_path=grading_dir / "cycles.json",
    log_dir=work_dir / "logs",  # 不保存日志可省略
)
```

`Match` 的参数为 `seed, a, b, labels=("A","B"), name="", display_names=("", "")`。a 为甲、b 为乙，每局新建两个常驻选手进程。`labels` 是机器身份键，`display_names` 是日志可读名（例如模型名、第几档对手），不填时回退到 labels。调用者自行构建换边列表；公开 `arena.py` 已自动换边。返回列表与传入比赛列表顺序一致，每项字段同日志的 `result`；`winner=1/2/3` 表示甲胜/乙胜/平，`score` 按甲乙顺序。基础设施故障抛异常，不能自动改算选手输。

正式配置为 `jobs=8, cpus=0..15`：槽位0使用CPU 0/1，依次至槽位7的14/15。每个槽位依次处理编号slot、slot+8、slot+16……的比赛，CPU无重叠；程序启动前即绑核，不依赖线程抢任务顺序。裁判和桥接进程本身也限制在给定CPU池。当前阶段2a指定 `cpus=16..23, jobs=4`，24–27留给陪练开发者；阶段1的16–27、6局开发配置本轮不使用。

独立命令入口如下。比赛 JSON 是数组，每项包含 `seed`、`a`、`b`，可选 `labels` 和 `name`，程序路径使用绝对路径最清楚：

```powershell
python Grading\算法对抗\攻城略地\tournament.py --matches matches.json --report report.json --log-dir logs
```

默认 8 局并行、CPU 0–15、CPU 时限倍率 1。开发时加 `--jobs 6 --cpus 16-27`。`--build-dir` 默认当前目录的 `.arena_cache`，中间文件应显式指向开发工作区。`--calibration` 默认本评分目录的 `cycles.json`，`--time-scale` 默认 1。

`cycles.json` 存每个逻辑处理器的周期/CPU毫秒系数与原始测量数据，缺少请求 CPU 时先自动测量再开局，之后复用系数。每个 CPU 上启动已绑核的校准子进程，运行三个各约 500 毫秒的忙循环；同时读取 `QueryProcessCycleTime` 周期增量和 `GetProcessTimes` 的用户态+内核态增量（100ns 单位），每个样本算 `cycles/(cpu_100ns/10000)`，三个值取中位数。对局每回合的周期增量除以该固定系数。系数依赖机器，换机器时重新校准。`arena.py --calibrate --cpus ... --calibration ...` 可以显式重新测量。

阶段1只测了开发允许的 CPU 16–27，未在性能核 0–15 上跑校准或对局。正式使用 0–15 时必须先补测这些 CPU；自动补测会完成这一步。只要读取同一 `cycles.json`，全部提交使用相同固定系数。

首回合CPU计费从周期数0开始，包括启动和全局初始化，后续回合以上次完整交令时的周期数为基点，含回合间用量。交令墙钟始终从本方向程序发送该回合局面起算，进程创建的系统等待不算交令时间；首个局面在本方启动完成后立即发送，不等另一方启动。创建时间另记首回合的 process_setup_wall_ms/process_creation_wall_ms。CPU 超时后仍收掉当前回合响应并丢弃，不把它当成下回合命令；最多等至该回合5秒墙钟截止。超过预算的CPU用量持续扣后续预算。日志格式详见同目录 `日志格式说明.md`。

确定性来自固定种子生成器、固定命令和到达处理顺序、固定槽位、固定系数；工具不使用随机调度或随机裁决。真实 CPU/墙钟截止边界附近仍可能受操作系统调度和测量波动影响，固定计算量的正式基线应按方案保留足够时限余量。
