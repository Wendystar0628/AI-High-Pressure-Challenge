# 《操作系统嵌套》难度上限调研（Opus）

## 结论

1. **上限就卡在这里，下一代旗舰会顶满。** Opus 在 37 个分项里拿到 32 项（Claude 评分员）和 35 项（Sol 评分员）满分，只丢 1.3 分，丢的都是一两行能修的小事。
2. **98.7 基本名副其实。** 严格按题面算约 95–97。主体在第 62–67 分钟完成，第 84.8 分钟主动收工，还剩 5 分钟。
3. **主因在题面，其次是评分结构。** 题面允许一条通吃路线：全部系统状态放进一棵 JSON 树，内核和应用都是宿主 JS，每步同步推进。这条路线下，一致时点、确定续行、分叉独立这些最难的要求几乎自动成立。评分又是做到就满。评分员和限时都不是主因。
4. **题目不用换，要把“嵌套”做真。** 最值得做的是“内核是程序”：子系统的内核是父系统里一个被计费、可修改的程序。再加“飞控是被调度的进程”和内存配额，走现在的老路最高约 60 分，这个上限和模型多快无关。估计现在的 Opus 能拿 58–74 分，下一代 70–85 分，都没有实测。

**证据边界：** 只读了题面、评分记录、作品源码、git 历史和作答日志，没有启动任何作品。第二节“没查到”的几条是读代码得出的，没有复现。所有预估分都是判断。下文代码位置相对 `H:\AI_OneShot_Model\Claude\Opus5.5\操作系统嵌套\src\`。

## 二、98.7 是否名副其实

**确实做到的（源码和评分员脚本都支持）：**

- 逐级共享预算（`kernel/kernel.js:292–335`）、四层系统树、祖先暂停传播。
- 投送走 JSON 副本和消息往返（`kernel.js:855–927`）。
- 带版本的数据连接、快照恢复重绑定、分叉重映射。
- 120Hz 确定性飞行，接触部位决定损坏（`kernel/flight.js:318–360`）。
- 两位评分员都写了独立脚本，不是只跑作品自带测试。

**题面写了、评分员没查到的（静态判断，未复现，合计约 2–3 分）：**

- **程序的值操作按常数计费。** 赋值、建数组、比较都做完整 JSON 深拷贝，却只算 1 单位（`vm.js:395、445、542、545、577`），字符串拼接也是 1 单位（`vm.js:436`）。题面 2.8 要求计费覆盖实际工作。`let a=[0]; while true { a=[a,a] }` 这样的程序，读代码看能在一个时间片内拖死甚至撑爆渲染进程，根系统和兄弟系统一起受影响。这也违反“程序异常只影响相应进程”。
- **内建函数先做完再记账。** `split`、`join` 处理大字符串时整批执行，之后才补记费用（`vm.js:489–491`），正是题面禁止的做法。
- **分叉会改写用户数据。** 重映射会遍历邮箱内容（`snapshot.js:147–168`），未处理消息里恰好等于 `inner-1` 的字符串会被改掉，违反“分叉起初状态相同”。
- **暂停中的子系统还能被改。** 编辑器输入直接写 `app.text`，不走消息和调度，暂停时也能打字（`ui/apps/misc.js:171`）。
- **实际操作没走到的路径。** B 站视频播放两位评分员都没明确验证，本机保存和导入对话框也没人操作过。

**题面没写到、不算差的：**

- 子系统内核不花任何指令。
- 程序不能创建子系统、连接工作簿或投送（`kernel.js:1094–1225` 没有这些系统调用）。
- 没有内存预算。
- 所有系统共用一个 JS 堆，题面 2.10 明确允许。
- 失控段是按故障时长的正弦曲线（`flight.js:187–205`），题面不要求科研级仿真。
- 预算只影响画面进度，不影响飞行结局（`kernel/player.js:491–496`）。

## 四、怎样做到爆难（按“顶不满”的贡献排序）

### 方案一：内核是程序（28 分，决定性的一项）

**题面写法：**

> 根系统之下的每个系统都由一份内核程序运行。内核程序是存放在父系统文件系统中的普通程序文件，用 2.7 的程序格式写成，由父系统作为进程启动并调度。子系统的进程表、调度、等待与唤醒、消息投递、文件系统和系统调用分发都由这份程序实现；子系统再创建子系统，就是这份内核程序再启动一份内核程序。只有根系统的内核可以由宿主实现，宿主对子系统只提供程序执行环境和显示、输入设备。
>
> 内核程序的工作和普通程序一样消耗执行预算并计入父系统读数，任务管理器分别显示每层内核自身和用户程序的消耗。
>
> 内核源文件可以在父系统编辑器中打开、修改和保存，重启该子系统后生效：改变调度策略、增加系统调用、改变消息规则或文件行为，子系统的实际行为相应变化。内核写坏时该子系统显示内核错误并停止，父系统和兄弟系统照常运行，改回后可以重新启动。
>
> 桌面和应用同样由系统自己运行：窗口管理（窗口次序、焦点、命中判断与输入分发）和子系统应用（文件管理器、播放器、图表工作台）是内核启动的程序，经显示接口提交画面、经消息取得输入。程序的编译器也是系统内的程序，可以在系统内修改后编译自身。

**为什么难：**

- **现在的嵌套只是一本账。** `runHost` 是一个 JS 递归（`kernel.js:329–335`），子系统调度不花一条指令。Claude 实测“承载限 200 后子树合计恰为 200”，Sol 的脚本断言承载读数和子系统用量完全相等。精确相等说明没有内核在运行。
- **老路线改不了。** 内核约 1400 行 JS 在预算线之上，用户碰不到；应用全是 `services[...]` 宿主函数。
- **难在设计，不在功能多。** 如果每层内核都解释执行下一层，每层放大几十倍（估算），6000 单位/步到第四层不足一条指令，调大预算也只多撑一层。模型得自己想出：普通指令由根执行环境直接运行并逐级记账，只有调度和系统调用才逐层交给内核；定时抢占要跨层合并；一次系统调用要穿过三层内核。这是嵌套虚拟化的核心问题。
- **其他要求跟着变真。** 第二层的快照要由第一层内核程序一条条指令完成，不再免费也不再原子，一致时点和预算续行才真正冲突。这一项不用测帧率，就绕开了“宿主代码不花预算”的漏洞。
- **调试成本高。** 现在内核能在 node 里带堆栈调试（`tests/run-all.mjs`）。写进自定义语言后，错误要穿过自己的编译器和多层执行环境才能定位。

**向上空间：** 是一道楼梯，每级都能单独验证，做多少得多少：调度 → 系统调用与消息 → 文件系统 → 窗口管理 → 应用 → 编译器自举。顶满要把桌面、播放器和图表全写进自己的语言并调通，判断 90 分钟内做不完。内核若只是薄薄一层、实际调用宿主函数，改内核的验证自然过不了。

**评分（28 分）：**

| 分项 | 分值 | 打分点 |
|---|---:|---|
| 调度与进程表 | 7 | 修改内核源文件的调度逻辑并重启后，子系统进程的实际进展按新逻辑变化 |
| 系统调用与消息 | 5 | 内核源文件新增系统调用、修改消息规则后，子系统程序能使用且行为相应变化 |
| 内核开销进入预算 | 4 | 各层内核指令实际消耗父系统预算并可读，层数越深用户份额越小，第四层程序仍持续运行 |
| 文件系统 | 3 | 修改内核的文件逻辑后，子系统的文件行为相应变化 |
| 窗口管理 | 4 | 修改窗口管理程序后，所属桌面的焦点、次序或输入分发相应变化 |
| 应用程序化 | 3 | 修改文件管理器、播放器或图表程序后，界面与行为相应变化 |
| 编译器自举 | 2 | 在系统内修改编译器并编译自身后，新编译器生效 |

**怎样验证：** 一次评分内做得完，全是黑盒操作。比如把轮转改成只跑第一个就绪进程，看另一个 spin 的读数归零；加一个返回 42 的系统调用；把消息改成后进先出；写坏内核，看只有这棵子树报错。

**视频：** 很好看。在父桌面打开子系统内核，改一行，重启，行为立刻变了；写坏时子系统窗口里出现内核错误画面，旁边的动画照常播放。

### 方案二：飞控是被调度的进程（交互场景方向改为 14 分）

**题面写法：**

> 排演中的直升机是不稳定的被控对象：机体由物理步进演化，没有控制输入就会失去姿态。保持飞行的是子系统里的飞控进程，它是普通程序文件，经系统接口读取带时间戳的传感器值、写入总距与舵面，和其他进程一样竞争执行预算；错过周期的控制量不补发。
>
> 预算、调度和时间速率因此实际影响飞行：调低任一祖先的拨付、在同一子树运行持续计算或提高时间速率，控制周期变长，机体抖动、发散直至坠毁；及时恢复时可以拉回。修改飞控程序会改变飞行。评审会按说明自己写一个飞控程序，让直升机悬停并降落到第二个停机坪。风、目标航向与故障仍是排演输入，默认演出是预置飞控在默认拨付下的过程。排演记录保存实际发生的控制时序，从同一记录位置分叉后给不同预算或输入，形成各自的结局。

**为什么难：**

- **现在预算不影响结局。** `player.js:491–496` 用循环补算，低预算只让画面变慢，撞不撞、撞哪里完全由输入表决定（`flight.js:102`）。
- **现在没有可失稳的对象。** `pitchWant`、`rollWant` 直接给目标姿态（`flight.js:216–221`），评审自写的控制器根本接不上。
- **闭环后记录的设计要重做。** 结局依赖实际调度，记录不能再只存输入（`player.js:343`）。回放和前后跳转要同时回到飞控进程的状态，或改为记录控制量，还要保住默认十秒。
- **对象要经得起未知控制器。** 评审自写飞控能降落，说明动力学和接口不是为自带控制律手调的。

**向上空间：** 连续的。自写飞控能完成多难的任务（悬停、定点降落、带风降落）、物理是否可信，评分员看实际结果给分。

**评分（14 分）：** 飞控是被调度的程序 4；预算与时序改变飞行结果 4；记录、跳转与分叉续演 4；接触与部件结果 2。

**怎样验证：** 调低预算、运行 spin，看机体是否发散；写约 30 行飞控；同一位置分叉后给不同预算，比较落点。只看逻辑预算，不测帧率。

**视频：** 全片最强的一个镜头。在根系统任务管理器调低预算，第三层的直升机开始抖，最后摔下来。操作系统和直升机第一次有了因果关系。

### 方案三：内存与存储配额，失控程序不出界（并入“共享资源与隔离”12 分）

**题面写法：**

> 每个系统除执行预算外还有有限的内存和存储配额，同样逐级拨付、兄弟共享。程序的变量、数组、字符串、消息队列和进程、应用的缓存都占用内存，任务管理器显示实际占用；配额不足时分配失败，程序得到可处理的错误，或被系统结束。复制、比较、拼接等操作的工作量随数据大小计费。
>
> 评审会运行失控程序：指数增长的数组、循环创建进程、消息洪泛、写满存储、无限递归。受影响的只有它所在配额范围内的系统，范围外的操作、动画和表格照常。

**为什么难：** 这不是加一列读数。每个值的占用都要随赋值、消息、快照恢复、进程结束精确增减，播放器轨迹、图表缓存这些宿主服务也要入账。这是一条横贯全部内核的不变量，事后很难补，逼模型一开始就定内存模型。现状：`kernel.js` 里没有任何内存计量，邮箱也没有上限（`kernel.js:239`）。

**向上空间：** 有限但有台阶：配额不足时换出到存储继续运行；分叉共享未改动的内存，读数上能看出来。

**评分（12 分）：** 共享预算与逐级拨付 4；按规模计量与续行 3；内存与存储配额 3；失控程序的隔离 2。

**怎样验证：** 评分员写五个几行的程序，一次评分内做得完。

**视频：** 中等。内存条爆红，该子系统报错，旁边的动画照常。这是操作系统该有的隔离要求，不是防作弊。

### 方案四：界面方向给足向上空间（分值不变，只改指南一句）

Opus 16.4/17，但画面是低多边形矢量风格，离专业动画还很远（看过评分员截图 `flight-9.png`）。现在满分相对题面清单，不相对可达水平。

指南该方向开头加一句：**“按成品与专业美术、动画水准的距离给分，题面列举的内容齐全不等于满分。”**

能给顶部留 3–5 分，靠看截图和录屏就能评，视频里也最直观。这一句接近你撤销过的“水准锚点”，所以要你决定。它不设档次。

### 方案五：题面删掉逐条边界，只留不变式（不增不减分值）

2.12 第 3 条、2.15 第 3 条、2.16 第 2 条把边界场景写得像答案。改成一句不变式，例如“恢复只改变选定子树，范围外关系按逻辑身份保留，旧世代的消息不影响新世代”，具体场景放到评分员手里。这符合“不写能推断的内容”。估计对第一档只有 2–4 分作用，对中档更大。

### 备选：每棵一级子树一个独立操作系统进程

如果觉得方案一太偏离主题，可以换这个：`inspect()` 报告 PID，在 Windows 里结束该进程，只有这棵子树崩溃。它同样能打破单一 JSON 树，迫使模型面对跨进程的一致快照和远程显示。但这是做或不做的一道坎，没有楼梯，顶不满的作用弱，所以排在后面。

## 五、你的要求里哪些有影响

- **“不测帧率和吞吐”不妨碍。** 但它解释了为什么之前加预算项没有用：宿主代码不花预算，再多预算规则都能用“宿主 JS + 自报成本”通过。方案一把内核搬到预算线以下，不测吞吐也成立。
- **“朴素评分”不妨碍方案一到三。** 都是一句打分点加评分员动手操作。只有方案四碰到边界。
- **题面的许可要改一处。** 2.1 的“宿主可以提供绘制与交互后端”保留，但要补“只有根系统内核可以由宿主实现”。这是这次最关键的改动。
- **“不写实现方案”不冲突。** “改内核文件后行为变化”对任何实现都成立，属于产品要求。
- **限时不要动。**

## 六、风险

- **界面可能退步。** 模型把时间花在内核上，界面观感可能下降，甚至影响视频；窗口管理写进自定义语言时尤其如此。这要看试跑结果。
- **弱模型可能几乎拿不到方案一的 28 分。** 分差会明显拉大，这符合本意。
- **预估都没有实测。** 建议改完后由 Sol 和 Opus 各跑一次再定权重；如果 Opus 仍高于三分之二，把方案一的分值继续调高。
