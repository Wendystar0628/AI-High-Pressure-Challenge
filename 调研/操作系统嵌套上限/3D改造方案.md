# 《操作系统嵌套》3D 改造方案

**依据版本：** 11 月 3 日 0:30 改完的“内核是程序”版题面和指南，下文的原句都出自这一版。

**证据边界：** 只读了文件，查了 Chromium 源码和 Electron 文档，没有启动任何东西。工作量估计和第六节的判断都没有实测。`视频导出方案.md` 写这份报告时还没出来，2.17 新增的标识等它出来再对一次。

## 结论

1. **做得到，主题和分值都不用动。** 把显示设备升级成能接收三维场景的设备：Three.js 放在宿主一侧的设备里，程序只经系统调用提交可复制的数据。这和 2.7 的“宿主对子系统只提供程序执行环境和显示、输入设备”不矛盾。
2. **一条语义解决大部分一致性：画面只由已提交的内容决定。** 相同的提交得到相同的画面，两次提交之间画面不变，宿主不推进场景。暂停、单步、跳转、快照和投送的一致性都从这一条来。
3. **预算线划在提交上。** 机体、部件和碎片的计算、粒子发射、资源载入、经各层内核分发都计费。绘制不计费，但几何、贴图、实例和粒子规模占内存配额。
4. **3D 带来一个和方案一同类的新难题：显示数据怎样穿过嵌套。** 一帧约 100 个节点加发射记录，约 1–2 千个数；逐层复制三次是 3–6 千单位，而 Opus 现在一个逻辑步才 6000 单位。这个难题不用另写要求，计费规则会自然逼出来。
5. **强模型的基础已经有了。** Opus 的 `flightgfx.js`（924 行）就是把三维部件投影成 SVG，物理和粒子发射记录也是三维的（`flight.js:84`）。七件作品运行时都没用 WebGL（Opus 只在离线渲染壁纸时用过），但查过的四件渔港作品都拿到了 Three.js（npm 或随项目打包）。估计强模型 3D 增量约 15–25 分钟。
6. **最大的视频风险是黑屏，不是做不出来。** 评分提示词现在没写遮挡参数，无论是否改 3D 都要补（第五节）。
7. **造型和演出维持 3+3，界面总分 17 不变。** 共改 11 个分项的打分点，其中 2 个改名（第三节）。

### 和初步判断的不同

| 初步判断 | 我的结论 | 原因 |
|---|---|---|
| 粒子计算走预算 | 只有发射记录走预算，粒子展开归绘制 | 逐粒子经内核提交，预算会被烟尘吃光，画面又最差。Opus 现在已是发射记录加按时刻展开，跳转和快照都简单 |
| GPU 绘制不计费 | 同意，但要补一条：绘制规模占内存配额 | 否则一次很小的提交就能要求十亿个实例，拖垮 GPU，破坏“范围外照常” |
| 3D 场景是独立资源 | 同意，再加两条：资源里不含宿主代码；材质、变换、相机和时序能用编辑器改，说明里有最小场景的写法 | 否则交一个二进制文件或一段 JS，评分员无法验证“改资源画面就变” |
| 活跃上下文每页约 16 个 | 按渲染线程算：主线程 16 个，Worker 4 个；`--max-active-webgl-contexts` 可以调高；被挤掉的是最久没绘制的上下文 | 暂停或被盖住的视图先黑。题面写成“超过也要全部正确”，作品自己加开关也算解决 |
| WebGL 画布可能和网页视图一样空白 | 两者要分开看，主文档里的画布大概率不受同样影响，待实测 | 见第五节 |
| 无 | 补两条闭环衔接：物理落后不能变成慢动作；相机是应用状态 | 前者会让“调低预算坠毁”退化成“调低预算变慢”，这正是旧方案的问题 |

## 一、核心语义

三维内容分三层，只有前两层是系统状态。屏幕上的画面任何时候都能只从前两层重建。

| 层 | 内容 | 归属 | 进快照 |
|---|---|---|---|
| 场景资源 | 几何、部件层级、材质、贴图、灯光、镜头、时序 | 系统文件；载入后占所属系统内存配额 | 是 |
| 场景状态 | 节点变换、损坏、碎片、发射记录、相机、时刻 | 源进程 | 是 |
| 设备缓存 | Three.js 对象、GPU 缓冲、图形上下文 | 宿主，可随时丢弃重建 | 否 |

**数据量、频率和预算、配额的关系：**

| 动作 | 执行预算 | 内存或存储 |
|---|---|---:|
| 打开场景 | 读文件、解析、载入按规模计费，可跨多个逻辑步 | 已载入量占内存；不足时载入失败，播放器报错 |
| 逐次提交 | 按本次数据规模计费，各层内核分发的工作计入该层读数；预算不足时提交变稀，错过的帧不补画 | 未交付的提交占内存 |
| 物理、损坏、碎片、发射 | 计费 | 状态占内存 |
| 绘制、粒子展开、着色 | 不计费 | 规模占内存 |
| 投送 | 资源复制和逐次转发都算源系统 | 算源系统，目标只出外框 |
| 快照、分叉 | 父系统付（2.12 已写） | 占父系统存储 |

**各场景怎样保持一致：**

| 场景 | 语义 |
|---|---|
| 投送 | 目标视图拿资源副本和同一序列的提交，用自己的尺寸绘制。同一时刻、同一机位，宽高比只改变取景。后开的投送先拿资源再接当前提交，不重放历史 |
| 暂停、单步 | 没有新提交，画面不变。改变窗口大小或被遮挡后露出，设备按最后一次提交重画 |
| 快照、恢复 | 前两层进快照，设备缓存重建。恢复后第一次呈现就是保存时刻。范围外投送窗口里的旧资源不再使用 |
| 分叉 | 各有一份资源和状态，一边改材质或卸载不影响另一边（2.12 第 3 条已覆盖） |
| 跳转、回放 | 按记录重算到目标位置，算完前画面停在旧位置，算完一次切换。断裂的部件随跳转还原 |
| 记录 | “记录保留场景资源”不改：场景文件改了，旧记录仍按当时版本回放。怎样省存储由模型决定 |
| 默认演出 | 已是预置记录，结局不随预算变化，不用再改。低预算下画面可以落后，结局不变 |
| 窗口管理程序 | 命中判断把视图内坐标交给源应用，部件判定归源应用。窗口次序决定遮挡 |

**多实例语义（替换“SVG 引用独立”）：** 资源和状态按系统实例和应用隔离。两个播放器开同一场景，一个撞毁断尾，另一个不受影响；关闭一个，另一个的画面还在。源窗口和投送是同一状态的两个视图，见上表。

### 2.14 直升机场景与飞行排演

第一段末尾加：“默认演出和其他记录一样可以跳转和续演，转入排演时画面不跳变。”

五个阶段后加“场景空间”，并换掉“直升机造型”“画面与运动”和最后一段：

> **场景空间。** 场景是完整的三维空间：地形有起伏，两个停机坪、建筑或障碍、树木草地和远景都是有体积的对象。飞行接触发生在看见的这些几何上，改动资源里的地形或障碍，飞行结果相应变化。不要求飞行动力学或碰撞的科研级仿真精度。
>
> **直升机造型。** 采用紫色与黄色配色，以紫色机身和黄色识别涂装形成清楚的主体。机身两侧印有醒目的数字 **24**，贴合机身曲面并随表面受光。模型由可独立运动和损坏的部件组成：连续曲面的机身，透过玻璃可见座椅和仪表板的驾驶舱，舱门与机身分区的接缝，发动机舱与排气口，桨毂与桨叶，尾梁、垂尾与水平安定面，尾旋翼，起落架和连接结构。旋翼围绕正确的轴转动，近距离和任意角度观看都没有缺面、漏缝或穿插。
>
> **材质与光照。** 场景有确定的时刻和天气，决定主光方向和天空颜色。漆面、玻璃、金属、橡胶、地面和草叶的反光与粗糙度各不相同，玻璃透明并映出环境；撞击和燃烧后漆面熏黑，断口露出内部结构。直升机和碎片有实时投影，落在起伏的地面和自身上，旋翼的影子扫过机身，投影随离地高度变化。
>
> **烟尘与碎片。** 下洗气流随旋翼高度和地面材质带起尘土、压倒草叶。碎片是有厚度的部件，沿各自轨迹翻滚、落地、弹跳后停稳，同样有投影。烟和火处在三维空间里：与机体和地形有正确的前后遮挡，随风偏移，火光照亮周围，烟遮住后面的景物。
>
> **镜头。** 场景带一组演出镜头，默认演出按它运镜；起飞、失控和撞击时直升机处在画面主要位置，数字 24 在主要展示阶段可辨认，相机不穿过地形和机体。排演用同样的镜头规则跟随实际飞行，撞到哪里，镜头就到哪里。
>
> **绘制。** 动态画面用 WebGL 2 或 WebGPU 实时绘制，不能用视频、位图序列或预渲染画面代替；模型和贴图由你自己制作，贴图可以预先生成。几何、材质、动画数据和播放行为分别能在资源文件与播放器中对应，支持暂停、拖动进度、逐帧、调速与快照恢复；不是点击“播放”后只执行一段无法控制的固定表演。

**共用一套场景的落点：** 默认演出和排演用同一个场景文件、同一个物理和损坏模型、同一套镜头规则。差别只在控制量来自记录还是飞控进程。

>    - 图形上下文可能丢失，丢失后画面从系统状态恢复，程序和播放位置不受影响。
>    - 评分和录制时，主窗口可能被其他窗口完全盖住。Windows 下 Chromium 会把被盖住的窗口当作隐藏，`<webview>` 等独立网页内容会变空白，动画帧回调可能停止。作品不能因此停止运行、停止绘制或留下空白画面。

## 四、一次评分内怎样验证

这些不写进指南，指南只放上面的一句话打分点。比较画面时看主要内容，不要求逐像素。

1. **资源：** 改场景文件的机身颜色后重开；打开第二份场景；按说明手写一个最小场景打开。
2. **同一时刻：** 直接跳到 7 秒截图；跳到 2 秒再跳回 7 秒截图；从 6.9 秒逐帧到 7 秒截图。三张一致，且没有后面时刻的碎片。
3. **宿主不偷跑：** 暂停所属子树，旋翼、烟和火全停。这时改变窗口大小、最小化再恢复，画面还是那一刻。
4. **预算：** 调低祖先拨付，`position` 和 `frameTime` 拉开，画面更新变稀，排演中的机体发散坠毁，而不是慢动作。
5. **配额：** 把子系统内存配额调到小于场景，打开时得到错误，范围外动画照常；调大后正常。
6. **失控：** 写一个不断载入或提交巨大场景的程序，范围外照常操作。
7. **投送：** 投送到根系统，同时刻同机位；在投送里拖动镜头、点选部件、点地面定航向，源应用相应变化。
8. **多实例：** 两个播放器开同一场景，一个跳到撞击后，另一个停在起飞；关闭其中一个。
9. **上下文上限：** 用脚本开 18 个以上三维视图（各实例的播放器加投送），逐个看有没有黑的。
10. **快照：** 撞击中途快照，跑到结束后恢复，比较画面；恢复后范围外投送窗口也回到旧画面。保存到本机，重启导入，还是那一刻。
11. **造型：** 用自由镜头贴近机身环绕，看缺面、穿插和数字 24。

## 五、系统坑与环境

**现有证据：**

| 事实 | 来源 |
|---|---|
| 作品窗口被盖住时，guest `document.hidden=true`，主窗口截图网页区全白；同时主文档 `hidden=false`，主文档其他内容（含 SVG）正常 | Sol 评分员评 Opus 的日志 148–166 行 |
| 命令行加 `--disable-features=CalculateNativeWinOcclusion --disable-backgrounding-occluded-windows` 后 guest 恢复 | Terra、Haiku 的评分记录 |
| Opus 自己在主进程加了 `CalculateNativeWinOcclusion`，也关了 `backgroundThrottling`，guest 仍然隐藏 | Opus `main.js:24、40` 加上述日志 |
| 七件作品的主进程里，6 件写了 `backgroundThrottling`，3 件写了 `CalculateNativeWinOcclusion`，说明强模型自己会碰到并处理这个问题 | 本次核对 |
| `backgroundThrottling` 关闭时主窗口保持 visible，`webview` 不受这个设置管 | [Electron 文档](https://ayakael.net/mirrors/electron/src/commit/a53e98c0f3cf736572e04cc804540d35831d9347/docs)（旧版镜像，和上面的实测一致） |
| 上下文上限按线程算；默认主线程 16、Worker 4；开关同时改两者；超限时丢最久没绘制的；只有别的上下文被销毁才恢复 | [Blink 源码](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/blink/renderer/modules/webgl/webgl_rendering_context_base.cc)、[默认值](https://chromium.googlesource.com/chromium/src/+/main/content/renderer/webgraphicscontext3d_provider_impl.cc)、[Chromium 开发者讨论](https://groups.google.com/a/chromium.org/g/graphics-dev/c/fmNedEEAYpA) |

**判断：** 主文档里的 WebGL 画布和主文档 DOM 走同一条合成路径，大概率能正常截到；如果模型把子系统放进 `<webview>`，里面的画布就会有同样的空白问题。

**评分提示词要补的一句**（`orchestrator\grader-prompt.txt` 第 20 行“桌面项目题”，现在这句只靠临时通知传达，没写在提示词里）：

> 启动时加 `--disable-features=CalculateNativeWinOcclusion --disable-backgrounding-occluded-windows --use-angle=d3d11 --ignore-gpu-blocklist`，不要加 `--max-active-webgl-contexts`。作品窗口被别的窗口盖住时，网页视图或三维画面可能空白：截图用 `Page.captureScreenshot` 截主窗口，不用 `canvas.toDataURL`；画面空白时先用 `Page.bringToFront` 把窗口提前再截一次，还是空白才算作品问题。

录制用同样的参数。录制本来就一次一份，保持窗口在最前即可。

**排期：** 这题评分和作答都要占显卡，不要和独占的性能评分同时进行。评分不测帧率，多窗口争显卡只影响等待时间。

**要实测的（性能测试结束后约 10 分钟，都用一个极小的 Electron 页面）：**

1. 主文档 WebGL 2 画布每帧换色，窗口被完全盖住，连截两张，看颜色是否更新。分别测带和不带参数、`backgroundThrottling` 开和关，记录动画帧回调次数和 `document.hidden`。
2. 同样的画布放进 `<webview>` 再测一遍。
3. 两个参数是否都必要。作品自己 `appendSwitch('disable-features', …)` 时，会不会盖掉命令行的 `--disable-features`（同名开关通常后者覆盖前者，所以提示词里还要带第二个参数）。
4. Electron 45.2.1 上第 17 个上下文的表现和 `--max-active-webgl-contexts` 是否生效。
5. `Page.bringToFront` 在 Electron 里是否真的把原生窗口提到前面；不行就把提示词这半句换成“保持作品窗口不被盖住”。
