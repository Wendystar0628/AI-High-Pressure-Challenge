# 《一道光谱》物理性能：测量方法与可行性（Sol）

## 结论与建议

**可以把固定规模下的内存作为资源效率证据；不建议把 GPU 利用率作为“越低越高分”的指标。还应补充实际完成的仿真工作量及其耗时，否则停算、慢算、减对象的作品反而占优。**

本报告按出题人最新更正设计：**评分 AI 以管理员身份直接启动独立的本机 Chrome，可用脚本、CDP 和 Windows 命令；不受浏览器 MCP 的工具范围限制。** MCP 仅是受测模型的开发工具。前期 MCP 实验只作环境对照。

建议正式评测只做一次：统一浏览器环境和一个规定的物理负载，恢复正常速度、完整效果，预热后采约 30 个一秒级样本。记录浏览器进程树的私有提交内存、GPU 进程专用及共享显存、实际规模和仿真时间推进；GPU 各引擎占用随记录保存，供解释现象。截图和需要时的短 trace 放在资源采样窗口外。无需为每个作品另做几分钟稳定性测试。本次重复和数分钟实验是测量方法验证，不是建议增加的评分流程。

| 指标 | 本机能否取得 | 建议用途 |
|---|---|---|
| 浏览器进程树 `PrivateMemorySize64` / Private Bytes | 能；包含渲染进程、Worker 所在进程、GPU 及服务进程 | **资源效率的主要内存证据**。它是私有提交量，不等同于当前驻留的物理 RAM；看预热后中位数及采样峰值，粗分档 |
| GPU 进程 Dedicated Usage、Shared Usage | 能，Windows GPU Process Memory 计数器有效 | 专用显存可作另一项资源证据；共享显存一起列出，防止只把资源移到系统内存。必须结合画面和物理内容解释 |
| JS 堆及 ArrayBuffer 后备存储 | CDP 能分别读页面与 Worker 的 isolate | 排查内存构成、增长和自报遗漏；**不宜独立给资源总分** |
| 完成固定仿真时间所用的真实时间、实际步数 | 有条件能；须识别真正的推进及完成边界 | **建议补充**。排除不推进、自动慢放及只提交异步任务；若用于效率比较，要明确步长和状态质量，优先按相同仿真时长归一化 |
| 主线程／Worker 每步物理耗时 | 能定位代码和线程时可测 | 经抽查可采用；异步提交时间不能冒充计算完成时间。CPU 采样 profiler 用于核实路径，不是精确的每步计时器 |
| GPU 每步纯计算时间 | 支持计时查询，但需圈定物理命令，极短任务会读到 0 | 合并若干步后取平均，适合作为解释和抽查；不是任意作品都能自动提取的通用分数 |
| GPU Engine 利用率、整卡 `nvidia-smi` 利用率 | 前者可按 PID；后者主要反映整卡 | **不按低值直接给高分**。提交频率、画面复杂度、GPU 计算替代 CPU、频率和其他引擎都会影响它 |
| rAF 回调频率、FPS | 能读，但本机并非恒定 60 | 本轮不评分，只检查测量环境和工作提交节奏。rAF 回调、绘制提交、实际呈现不是同一计数 |
| 短时内存上升趋势 | 能观察 | 只能提示问题，不能凭一条上升曲线断言泄漏，也不能凭几分钟不涨保证无泄漏 |

**不能从本次实验推出“低于若干 MB 满分”或“GPU 超过若干 % 就差”。** 本次负载是测量探针，不是完整参赛作品；缺少成品样本的资源分布。直接用倒数、最小值排名或严格线性换分，会奖励内容少、贴图少、不做物理甚至不出新画面的实现。

### 固定的应是物理任务和可见质量

固定数量只解决了部分问题。至少要同时固定以下条件，作为一个简短的测试负载说明：

- **物理任务**：同一节点／状态、同种投放物及数量、尺寸质量、投放区域和初始运动、容器水量及主要参数、正常速度、相同的仿真时段。处在空中碰撞、浸水耦合和已经落稳，计算负担完全不同；不能只写“投放 200 个”。具体数量应由出题人定，本报告没有用探针实验替作品标定数量。
- **场景延续**：原有十环和其他仍在运动的装置继续按题意存在；投放物相互作用并作用于机关、液体，期间不减少、藏起或失去交互能力。抽查移动、扰动之后仍有响应；不以某种内部实现方式作为优劣依据。
- **视觉条件**：同一视口、DPR、机位和面板／辅助显示状态；相同完整画面档位，实际画布与内部渲染分辨率不动态下降，材质、阴影、透明与光效没有因测试被撤掉。不同作品的美术成本仍不可能完全相同，资源分数应粗评“是否值得”。
- **物理与显示精细程度**：不能强制所有作品用同样的流体粒子数、网格数或迭代数。这会规定实现手段，而且不代表同等精度。题面写可见的精细程度、交互现象和精度保持；自报的内部规模用于核验，不直接作为跨算法的等价工作量。

建议题面只补充这些可观察的内容、实测读数的含义和统一运行环境；不写测量算法、CDP 接口、计时 API 或实现结构。评分指南只需简短说明：在规定负载和完整效果下，以外测内存、显存及有效仿真推进综合看效率；低占用本身不代表优秀，GPU 利用率仅供解释；自报和实际不符、测量时减规模或降精度，在性能相关分项处理。具体处罚留在指南，不放题面。物理或美术内容的缺失仍归原分项，性能项不要再重复扣同一件事；缺少必要内容的测量结果不与合格负载直接比较。

### 1. 物理计算：计提交、计完成、计设备执行，差别很大

主线程固定算术负载对 1024 个数做同样的循环，预热后每批 50 次，共三批；批总耗时为 **73.6、72.4、72.5 ms**，平均到每次为 **1.472、1.448、1.450 ms**，批均值极差约为均值的 **1.6%**。单次读数受约 0.1 ms 的页面时钟粒度影响，中位数为 1.4–1.5 ms。这只是固定算术探针，没有模拟完整的碰撞、流体或十环机关。

异步实验把“主线程提交”“后台实际执行”“结果可用”分开测，直接 Chrome 重复 10 次：

| 探针 | 提交时间 min／中位／max（ms） | 实际后台时间 min／中位／max（ms） | 主线程等到完成 min／中位／max（ms） |
|---|---:|---:|---:|
| Worker：约 8 ms 忙循环 | 0／0.05／0.20 | 8.0／8.0／8.4 | 8.1／8.2／8.6 |
| WebGL：固定片元计算 | 0／0.10／0.20 | 0.193536／0.195072／0.195584 | 5.9／6.0／9.5 |

Worker 的后台时间取 Worker 自己的时钟差；另用外部 trace 抽查 20 次 `worker.js` 的 `onmessage`，事件耗时为 **7.863–8.975 ms，中位 7.9665 ms**，并能在独立 Worker CPU profile 中定位到该函数。WebGL 的设备时间来自 `EXT_disjoint_timer_query_webgl2`；完成时间来自 fence 异步轮询。后者包含命令排队、轮询、事件循环唤醒，不能与纯 GPU 时间混称。

WebGPU 实际可申请 `timestamp-query`。极短的单 dispatch 查询读到过 0；另一次计算确认输出值非零、没有着色器编译或验证错误。把同样的 dispatch 放在一个 pass 内重复 100 次，四次计时均为 **0.458752 ms／批**。另开浏览器启用开发计时标志后为 **0.427008–0.430848 ms／批**。这里不能用不同浏览器两组小数直接判定优化收益；它证明的是短任务须批量计时，“0”可能只是计时分辨率。Chrome 官方也说明 GPU 时间查询有量化，应区分设备计时与提交／完成等待。[Chrome WebGPU 计时说明](https://developer.chrome.com/blog/new-in-webgpu-121)，[GPUQueue 完成语义](https://gpuweb.github.io/types/interfaces/GPUQueue.html#onsubmittedworkdone)。

落地时必须先确定读数的含义：

1. **单步延迟**：从发起该步到本步所需的 Worker／GPU 结果全部可用。并行任务计关键路径，不能把多个 Worker 的重叠时间相加当作延迟。
2. **设备或线程计算量**：各线程 CPU 执行时间、GPU 物理 pass 的执行时间。它们是不同量，不能简单相加当成端到端耗时。
3. **持续吞吐**：一批工作全部完成的真实时间 ÷ 实际推进的仿真秒数。允许内部流水和并行，不应为测每一步强行同步，破坏其正常工作方式。

如果要比较作品效率，优先使用第 3 个量，同时记录实际步数与步长。单纯“每内部步更快”会奖励步长、精度或计算范围不同的实现。若按正常实时播放测吞吐，所有合格作品都约为 1 倍实时，只能证明跟上了时间，不能区分余量；测计算余量要有一个**不等待播放节奏的、可等待完成的批量推进边界**。已有的单步功能可作为定位入口，但人工或 CDP 逐次点击的往返开销不能算作物理计算成本。

**有 CDP 也没有一个“自动给任意网页的物理 step 精确计时”的通用命令。** 评分 AI 仍须看源码识别推进函数、消息完成、物理 GPU 命令与呈现之间的边界。没有这一步，就只能可靠测整页 CPU／GPU 负担，不能宣称测到了每步物理。主线程采样、Worker profile、GPU 进程线程忙时，都不能自动完成这种语义划分。建议只抽查一个代表性边界；若组织方不愿提供可复用适配，应把每步耗时作为待核实的作品读数，而非主要排名指标。

### 2. 内存与显存：可外测，但口径不能混用

向同一浏览器依次增加已触碰的内存，CDP 读到的构成为：

| 状态 | 主页面 JS usedSize | 主页面 backingStorageSize | 外测浏览器私有提交量（窗口均值 MiB） |
|---|---:|---:|---:|
| 基线 | 1.19 MiB | 约 0 | 340.1 |
| 增加 64 MiB Uint8Array | 0.65 MiB | 64.01 MiB | 392.5 |
| 再向 Worker 分配 64 MiB Uint8Array | 0.65 MiB | 64.01 MiB | 437.2 |
| 再增加约 32 MiB 普通数值数组 | 32.65 MiB | 64.01 MiB | 470.0 |

这些进程差值不是精确的分配尺寸，期间还有 GC、缓存和驱动变化。外测能看到 Worker 增加的负担，而主页面读数看不到；另行附加 Worker 后，它的 `backingStorageSize` 为 **64.0003 MiB**。本实验的页面 `performance.memory` 在分配页面 Uint8Array 后包含了其后备存储，但并未包含 Worker 的 64 MiB，不能把它当总内存。

CDP 的 `Runtime.getHeapUsage` 按 isolate 返回 `usedSize`、`totalSize`、`embedderHeapUsedSize`、`backingStorageSize`。须发现并附加 Worker／独立 frame，按 `Runtime.getIsolateId` 去重；不能把每个 frame 的同一 isolate 重复相加。本机实验还发现：只枚举顶层 target 会漏掉 Worker，给页面启用 `Target.setAutoAttach` 后才能取得完整目标。`performance.measureUserAgentSpecificMemory` 在普通未跨源隔离的测试页面不可用，不能要求评分时随手调用。[CDP Runtime](https://chromedevtools.github.io/devtools-protocol/v8/Runtime/#method-getHeapUsage)，[performance.memory 的范围限制](https://developer.mozilla.org/en-US/docs/Web/API/Performance/memory)。

独立的 GPU 分配实验中，创建并**实际渲染写入** 16 张 1024² RGBA8 纹理，逻辑尺寸合计 64 MiB：

| 窗口（每窗 3 个样本） | GPU 专用显存 MiB | GPU 共享显存 MiB | 浏览器私有提交均值 MiB |
|---|---:|---:|---:|
| 基线 | 49.004 | 2.977 | 322.697 |
| 刚写入纹理 | 116.441–116.504 | 66.664–66.695 | 455.125 |
| 随后同一状态，第 1 窗 | 115.254 | 66.664 | 403.384 |
| 第 2 窗 | 115.254 | 66.664 | 402.382 |
| 第 3 窗 | 115.254 | 66.664 | 402.457 |

预热后的三窗显存相同，私有提交均值极差约 **0.25%**；刚分配时 CPU 侧临时量显著更高。另一个只申请／上传但未实际使用的纹理实验，没有对应增加同量的 Dedicated Usage。**逻辑资源字节数、系统提交量、GPU 当前驻留显存不是同一量。** 这既说明 Windows 计数器可用，也说明必须固定是否真正使用资源和采样时机。

口径建议：

- 内存主值为独立 Chrome 进程树的 Private Bytes 总和，并拆列 renderer、GPU process。它包含 V8 堆之外的原生数据、驱动和缓存，Worker 放到另一个进程也不会漏掉。枚举进程时核对根 PID、父子关系、进程名和创建时间，避免 PID 复用混入外部程序。独立 profile 也不保证没有浏览器附带后台任务：本次还见到 `chrome-extension://` 的 service worker，作品堆统计应排除它，整树内存则仍含浏览器开销，故只适合固定环境下粗评。
- `Get-Process.WorkingSet64` 是包括共享页的工作集。直接把多个 Chrome 工作集相加会重复计共享映像；若还要物理驻留口径，可另采按 PID 映射的 `Process\Working Set - Private`。不要把本报告的 Private Bytes 写成“实际物理内存”。
- Dedicated／Shared Usage 分开记录。以独立浏览器 GPU 进程为主要归属，检查其他自有 PID 是否也有非零占用；不要将所有进程显存相加宣称是去重后的整卡使用量。Windows 官方说明跨进程共享资源可能被重复计入。[Windows GPU 计量口径](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/)。
- 不把 CPU 私有内存、GPU 共享显存和专用显存直接相加成“总占用”，也不允许专用显存减少但共享显存暴涨就自动获益。进程树绝对值为主；同一浏览器的空页／加载前差值可作参考，不能扣掉作品在加载时就分配的全部资源。

### 3. 连续几分钟：能发现明显留存，不能见涨就判泄漏

先保持固定分配、停止额外数据记录，200 个一秒级采样点实际跨度 **219.71 秒**。浏览器私有提交的头五点中位为 **534.254 MiB**，尾五点中位为 **551.262 MiB**；后半程各 30 秒窗口中位约 **549–551 MiB**，没有持续等速上涨。初期增加约 17 MiB 并不等于泄漏。

作为阳性对照，每秒保留约 2 MiB 普通数组，页面堆在 0／10／20／30 秒分别为 **32.640／52.637／72.637／92.637 MiB**；外部进程私有提交也从头五点中位 **575.938 MiB** 升到尾五点 **619.207 MiB**。OS 采样有启动延迟，窗口覆盖并不正好是数组开始增长的 30 秒，不能用这两个端点反推精确分配速率。

另做了持续推进 1024 个简化弹跳对象、120 个物理步／仿真秒并持续绘制的三分钟实验。采集起止的仿真时间约为 10.008／190.008 秒，相差 **180.000 秒**，实际经过时间约 **179.992 秒**；总步数增加 **21600**。页面堆每 15 秒读取一次，在 **0.638–1.530 MiB** 之间呈 GC 锯齿，末值 **0.783 MiB**。181 个 OS 采样点实际跨度为 **195.98 秒**，包含 CDP 三分钟读数之外的头尾；私有提交头五点中位 **309.215 MiB**、尾五点 **291.820 MiB**，但中后段 30 秒窗口中位又从约 **266 MiB** 上升到 **292 MiB**。其中浏览器主进程从约 **52.8 MiB** 上升至 **70.6 MiB**，GPU 进程只从约 **92.6 MiB** 变为 **93.5 MiB**；不能把整树的增长全部归到物理数据。这组数据不能被简化成“内存绝对平稳”或“持续上涨所以泄漏”：固定仿真数据、JS 堆与整进程的曲线本来就不同。

结论是看**固定状态、固定对象数、固定记录容量下的后段低水位是否继续抬升**，并找可达对象或未释放资源佐证。单次短测中的峰值、GC 锯齿、首次着色器／纹理缓存、逐渐增长的记纹鼓，都不能单独证明泄漏。正式评分不必照搬本研究的数分钟测试；正常审阅期间可顺手再读一次，若没有持续增长的直接证据，就不额外扣“泄漏”。堆快照会暂停／扰动执行，不放在资源计分窗口中。

### 4. GPU 引擎占用：固定频率也有波动，频率不固定更不可比

在同一直接启动的 Chrome 中，用同一画布、同一片元程序，保持轻载 rAF 约 160 Hz，只改变实际绘制提交频率。每窗 5 个有效 Windows 样本，三次重复：

| 实际绘制次数 | 三窗最忙 GPU 引擎的平均利用率 | 三窗平均私有提交 MiB | 专用显存情况 |
|---|---|---|---|
| 40 次／秒；8 秒各绘制 320 次 | 0.128%、0.172%、0.132% | 330.0、349.4、303.8 | 41.27 MiB 起，第二窗短暂升至 59.62，后回到 41.53 |
| 160 次／秒；8 秒各约 1281 次 | 0.416%、0.531%、0.703% | 306.2、308.6、304.8 | 41.49–41.53 MiB |

40 Hz 三窗均值极差约占其均值 **31%**，160 Hz 约 **52%**；因为负载很轻，绝对差仅分别 **0.044、0.287 个百分点**，不宜把相对波动理解为重负载误差。它足以说明不能用个位小数百分比给作品排序；即便固定提交节奏，也需要足够的采样窗口和宽容的解释。

同样工作每秒提交更多，GPU 占用就更高。若不固定节奏，高占用可能只是更努力出帧；低占用也可能是丢提交、少算、只出旧帧。即使固定节奏，透明、阴影、反射、抗锯齿、像素数和美术复杂度仍不同，GPU 物理也可能换来更低 CPU 时间。利用率还是“某引擎忙了多久”，不代表计算质量或完成了多少等价任务。

本机能按 `pid_..._luid_..._phys_..._eng_..._engtype_...` 找到 3D、Copy 等引擎。**3D 与 Compute 不能机械相加当成一个总百分比**，更不能只找名为 Compute 的实例：计算着色器可能在图形引擎执行。最简展示为各引擎均值／采样峰值，加一个最忙引擎值；多个自有进程使用同一物理引擎时，需先按物理引擎归并，不能混淆引擎和进程维度。[Windows 官方说明](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/)。

`nvidia-smi` 本机整卡查询可用，但默认进程列表显存为 `N/A`；`pmon -s um -c 1` 虽能列出进程，Chrome 的 SM／内存利用率为 `-`，fb 为 0，不能把它解释成 Chrome 不占显存。这与 NVIDIA 对 WDDM 进程显存不可得的说明一致。因此用 Windows 计数器作进程归属；整卡 `nvidia-smi` 只用于核对设备和背景状态。[NVIDIA-SMI 官方说明](https://docs.nvidia.com/deploy/nvidia-smi/)。

### 5. 无窗口出帧：没有“必然封顶 60”这个前提

| 环境／负载 | 实测 rAF 次数／秒 | 说明 |
|---|---:|---|
| 现有 MCP，空载及 2 ms 主线程工作 | 约 160 | 相同回调频率掩盖剩余计算余量 |
| MCP，10／22 ms 主线程工作 | 99.12／45.14 | 负载超过时间预算后仍会下降 |
| 直接 Chrome，空载及 2 ms 主线程工作 | 160.01／160.02 | 与 MCP 对照一致 |
| 直接 Chrome，10／22 ms 主线程工作 | 98.81／45.14 | 主线程和页面行为影响节奏 |
| 另开直接 Chrome，加入 `--disable-frame-rate-limit --disable-gpu-vsync` | 连续三窗 58.57、41.64、32.18 | 解除限制并没有得到固定的、更高的回调频率；不据此假定恒定自由运行吞吐 |

最后一组是在当前负载条件下的观测，不据此推断这两个标志在所有版本都变慢。也试过给 `--screen-info` 添加 `refreshRate=60`，该版本未能启动；普通本机 Chrome 的 `HeadlessExperimental.beginFrame` 返回方法不存在。不能把旧 headless shell 的帧控制流程当成这台机器上已验证可用的方案。官方的 headless 虚拟屏参数也没有承诺以设置分辨率来固定刷新节奏。[虚拟屏说明](https://developer.chrome.com/docs/automation-and-testing/headless-screen-config)。

因此正式资源测量保留同一正常启动配置、正常页面节奏，不为“解除 FPS 封顶”修改作品。记录真实提交与仿真推进作为解释。若出题人坚持用 GPU 百分比横比，光设 Chrome 标志不足以解决；还得规定并核实相同的输出任务和节奏，这会增加测量约束，收益不如改用完成固定仿真工作的耗时。

## 评分 AI 可实际采用的最简方法

### 一次采集，不靠作品的资源读数

工作目录已有经过实跑的原型 `grade-capture.mjs`、`cdp.mjs`、`sample.ps1`。它们无需新增 Node 包，使用本机 Node 24 的 WebSocket、CDP 和 PowerShell。脚本在实验目录内输出独立 profile、前后截图、CDP 堆读数、按 PID 保存的 OS 样本，并通过 `Browser.close` 关闭自己启动的 Chrome。报告没有把这些脚本放入项目；正式采用前宜由组织方将已检查的工具固定保存到评分工具目录。

```powershell
# 切到本报告上面列出的实验工作目录；网页由作品自己的本地服务提供。
node .\grade-capture.mjs http://127.0.0.1:作品端口/ 30 .\该作品的负载设置.js
```

`30` 是采样点数，约每秒一次，实际时长以 JSON 时间戳为准。本次 200 点实际为 219.71 秒，不能把 `MaxSamples` 直接当秒数。一次采集的操作只有：**设定规定负载 → 预热约 10 秒 → 一次系统采样 → 看前后截图和状态是否一致**。负载设置脚本仅在评分侧操作已有界面、读取真实状态，不改作品；本次用自己的探针网页和 5 点窗口验证过完整采集流程，页面和 Worker 堆均成功取得。对真实作品仍要根据其现有 UI／源码适配投放和状态读取，不能假设所有作品都有相同的变量名。

若不用这个原型，最小的等价系统命令如下。新建独立 profile 并保留根 PID，不能附到日常 Chrome：

```powershell
$profile = Join-Path $env:TEMP ('phys-grade-' + [guid]::NewGuid())
$chrome = Start-Process 'C:\Program Files\Google\Chrome\Application\chrome.exe' `
  -ArgumentList @('--headless=new','--use-angle=d3d11','--do-not-de-elevate',
    '--remote-debugging-address=127.0.0.1','--remote-debugging-port=0',
    "--user-data-dir=$profile",'--no-first-run','--force-device-scale-factor=1',
    '--disable-background-timer-throttling','--disable-renderer-backgrounding',
    '--disable-backgrounding-occluded-windows','--window-size=1920,1080','about:blank') `
  -WindowStyle Hidden -PassThru
# 等 DevToolsActivePort 出现；其两行给出本次 CDP 端口与 browser WebSocket 路径。
Get-Content (Join-Path $profile 'DevToolsActivePort')
```

CDP 连接后，建作品页，`Emulation.setDeviceMetricsOverride` 固定 CSS 视口 `1920×1080`、DPR＝1（仅 `--window-size` 不能保证内页尺寸）。设好规定负载。然后一次运行实验目录内的命令：

```powershell
powershell -NoProfile -File .\sample.ps1 -RootPid $chrome.Id -Seconds 30 -Out result.json
```

该脚本实际调用的是：

```powershell
Get-Counter -Counter '\GPU Engine(*)\Utilization Percentage',
  '\GPU Process Memory(*)\Dedicated Usage',
  '\GPU Process Memory(*)\Shared Usage' -SampleInterval 1 -MaxSamples 30 -ErrorAction Continue
# 每个样本同时对已核实的 Chrome PID 列表读取：
Get-Process -Id $chromePids | Select-Object Id,PrivateMemorySize64,WorkingSet64,CPU
```

GPU 样本按自有 PID 过滤，保留引擎与适配器标识；仅使用 `Status=0`、有限且有效的样本。**进程在全机出现／退出时，通配符 Get-Counter 曾报无效样本错误**；脚本需保留错误和样本状态，不能因一条错误把整窗当 0。若自有 GPU 计数器缺失，结论是本窗该指标不可用，不能记成零占用。进程变化时重新核实归属；不要按进程名批量结束进程。

堆读数只需采样前后各做一次：

```text
Target.setAutoAttach({autoAttach:true,waitForDebuggerOnStart:false,flatten:true})  // 对页面 session
Target.getTargets() → 对 Worker／独立 frame 等 Target.attachToTarget(flatten:true)
Runtime.getIsolateId() + Runtime.getHeapUsage()  // 各 session，按 isolate 去重
```

需要抽查物理读数时，再对代表性过程采一段短 trace／CPU profile：

```text
Tracing.start({categories:"devtools.timeline,blink.user_timing,v8.execute,disabled-by-default-v8.cpu_profiler",
               transferMode:"ReportEvents"})
// 完成一小段正常仿真或一个可等待完成的物理批次
Tracing.end() → 保存 dataCollected，等 tracingComplete
// 若需函数采样，附加对应线程 session 后：Runtime.enable → Profiler.enable → Profiler.start → 执行批次 → Profiler.stop
```

这一步用于找执行路径、消息边界和漏算，不把录 trace 时的资源占用拿去与普通运行评分。另一次只录短 trace 的验证，在约 **245 ms** 内完成 20 次 Worker 任务并收齐 trace，Worker 事件为 **7.899–8.886 ms，中位 8.0345 ms**，不需要长时间录制。GPU 若有物理 pass 的计时，抽查计时是否包住真实命令、结果是否异步读取、是否漏掉其他 pass；没有清晰边界时只报告端到端结果可用时间，诚实标明其中混有调度和排队。

### 自报抽查与减配防范的最小范围

外部内存和 Windows GPU 计数器由评分侧采集，页面伪造仪表数字不能改变这些读数。但页面仍可能通过少做事取得低占用，因此只抽查以下同一组证据：

- **工作真的完成**：正常速度的仿真时间与真实经过时间一致；步计数来自真实推进位置，抽查实际状态变化。只让时钟数字前进、重画旧状态或只完成异步提交，不算有效推进。
- **负载和效果真的保持**：采样前后核对实际物体列表、液体／绳链／光路状态及必要的画面条件，保留截图；抽查源码中自动改分辨率、精细程度、对象数量或停止更新的分支。只读 DOM 中自报的 N，或只数 draw call，都不能证明对象真实。
- **计时真的覆盖**：同步物理看实际入口和出口；Worker 看带对应请求标识的完成消息；GPU 看物理批次完成及设备计时。界面值与外部代表性抽查应在相同定义、相同负载下相符；不要求不同计时口径的小数完全一样。

截图不能证明所有对象都参与耦合，静态源码也不能保证实际运行到那条路径；两者与一次代表性互动、trace 相互印证即可。无需设计一套复杂反作弊系统，也无需在所有作品的副本里重写读数后再测完整性能。读数不可信时记录其不可信，资源部分采用独立外测，计算部分只采用能够核实的结果。

## 需要出题人拍板的问题

1. **是否接受 GPU 利用率只作诊断，资源效率主要看私有提交内存和专用／共享显存？** 我建议接受，不设置“GPU 越低越好”的线性得分。
2. **固定负载具体是什么？** 需要明确节点／时段、投放数量与初始状态、水量和主要参数、机位及完整效果；还要定义哪些可见精细程度和交互质量必须保持。数量不能由本报告的算术／纹理探针直接推定。
3. **是否把完成固定仿真工作的耗时纳入性能质量？** 若要区分已经实时运行作品的计算余量，须允许评分侧识别或适配可等待完成的推进边界；若不愿增加这种适配，就保留“实时推进属实”的核查，不把每内部步自报耗时当主要排名依据。
4. **资源分数采用怎样的宽档位及画面质量解释？** 建议先用少量完整作品标定再定档，本报告不支持现在承诺统一 MB 阈值。低于预算不自动满分，精度／效果更高的较大占用也不自动差。
5. **是否固定组织方的一套短采集工具、Chrome 版本和采样配置？** 建议固定；评分指南只保留几句口径和规则，工具承担进程识别、状态过滤、输出和单位换算。一次约 30 点采样即可；数分钟内存趋势不新增为必做稳定性测试。
