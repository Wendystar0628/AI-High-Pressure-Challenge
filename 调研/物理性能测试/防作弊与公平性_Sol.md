# 多物理连锁机关：固定规模性能测量的防作弊与公平性

日期：2026-10-30。研究范围：防取巧、跨技术路线公平性及最少核实办法。

**前提已按出题人的更正更新：评分 AI 在管理员账户下直接启动本机无窗口 Chrome，可用脚本、CDP、Windows 计数器和 nvidia-smi；不受浏览器 MCP 工具范围限制。** MCP 配置仅用于了解受测模型的浏览器环境。本文是建议稿，未修改题面、指南或评分表；候选负载与分值安排均不是现行规则。

## 一、结论与建议

### 1. 推荐测“完成相同工作时的资源预算”，不按最低占用排名

取消帧率评分是合理的。但把它直接替换为“内存越少、GPU 百分比越低越好”，仍然会奖励少算、少画、偷偷放慢以及把工作移到另一个处理器的作品。

建议采用下面的组合：

1. **固定一份公开的有效负载与画面条件**：数量真实、物体保持作用、液体和机关继续运行，正常速度推进。低占用必须建立在这些条件成立的基础上。
2. **主存与图形内存分开记录、按宽档预算评价**：主存看专用 Chrome 进程树的私有提交量；图形内存同时记录专用与共享用量。它们都是系统侧的占用口径，不冒称精确的“页面总内存”。
3. **GPU 利用率只留作解释和异常线索，不单独给分**：高利用率可能是更完整的画面、GPU 计算或有效并行；低利用率可能是等待、少画、CPU 瓶颈或未推进。它也不是显存占用、算力效率或能耗的同义词。
4. **保留正常速度下的真实推进核实，不恢复帧率测试**：由评分脚本的墙钟确认仿真确实向前，并核实少量物体状态，不能只看页面上的时间数字。
5. **只做一次短测量**，配合已有源码阅读中的定点核实。无需探测最大规模、长时间泄漏测试、反复重跑取最好值或要求参赛者提供专门的底层测量框架。

这能筛出明显浪费和冒充负载，不能提供严格的跨作品效率排行榜。作品的水体、材质、阴影、光谱和状态记录仍有自由度；即使刚体数量相同，完成的工作也并不完全相等。资源结果应当回答“这份工作花得是否合理”，不能替代物理与美术评分。

### 2. 固定规模必须同时固定什么

“256 个对象”“精度滑块开到 50%”“使用同一个节点”都不足以单独构成固定负载。建议用一个**对用户可见的场景约定**确定以下内容，不规定算法、库、代码结构或数值方法。

| 维度 | 应当统一的内容 | 容易遗漏的差异 |
|---|---|---|
| 物体 | 投放数量、种类比例、尺寸、质量或密度、初速度与朝向 | 256 个可见实例可能只有 32 个有物理状态；对象池容量可能被当成存活数 |
| 空间和接触 | 投放位置相对容器的关系、相互间距、液面上方高度、投放批次 | 同样数量分散悬空、堆叠接触、进入水中，负载差别很大 |
| 场景 | 同一环节、同一初态，原有机关与其他部分继续保留 | 节点独立运行时，偷偷停止整个展厅其余部分 |
| 时间 | 正常速度，覆盖落水、波动、碰撞等活动阶段的一段固定区间 | 等物体全部静止以后才测；只更新仿真时间文字 |
| 画面 | 同一视口与 DPR、机位、辅助显示状态，保持选定的完整材质和阴影 | 缩小内部渲染尺寸后拉伸、关阴影、把相机转向空墙 |
| 质量 | 既有的三维作用、液体表现、绳链和光路细节保持成立 | 同名“高精度”滑块在不同作品中没有统一含义 |

**建议候选场景**：第 9 环晨池节点，保留整件装置，额外投放共 256 个物体，木块和黄铜块各半，覆盖浮、沉、接触和池水作用；选定完整画面档位、固定机位、辅助显示关闭，测活动中的一段短区间。具体尺寸、间距、批次和相对池面的高度必须在采用前定死；应保证不同合规布局都放得下且不会重叠生成。256 是待校准的候选数量，不是本实验得出的合适上限。

如果只测一个场景，这是较有代表性的选择，因为第 9 环已有吊桶、弹簧、吊绳、池水、浮镜与光路联动要求。它仍不能代表所有环节的资源表现，应在评分解释中承认这一点。不要拿这个局部读数推断全程最坏情况。

对液体、绳链、光线，建议记录各作品的实际规模，核实当前画面与物理要求，而不强行把“粒子数 = 网格点数 = 绳段数 = 光线数”当成统一工作量。要求相同可观察结果是题目内容；强制相同粒子、网格或步长则是在指定实现。若出题人需要数值上更严格的等价，应补充输出误差或可分辨细节的要求，而不是统一底层数量。现阶段只适合宽档比较。

### 3. 建议采用的外部读数与一次测量口径

| 读数 | 取法 | 用途与边界 |
|---|---|---|
| 主存 M | 专用 Chrome 根进程及所有后代在同一采样时刻的 `PrivateMemorySize64` 之和 | 主指标，包含渲染、Worker 所在进程、GPU 进程等的私有提交；不是物理驻留 RAM，也不是含全部共享映射的精确总内存 |
| 工作集 W | 同一进程树的 `WorkingSet64`，另列 | 辅助核实；直接相加可能重复计入共享页，不能作为替代 M 的精确总量 |
| 专用图形内存 D、共享图形内存 S | Windows `GPU Process Memory` 的 `Dedicated Usage`、`Shared Usage`，按本次浏览器 PID 归属筛选 | 两者都要看；不能只看 D 而放任换到系统共享图形内存 |
| GPU 引擎活动 U | `GPU Engine` 中本次 PID 的各引擎活动，保留引擎类型 | 诊断，不评分；不只看 3D 引擎，不把不同引擎百分比简单相加 |
| 实际推进 T | 外部单调墙钟 + 约定状态的前后变化 | 防放慢、停算和后台排队；不是每帧耗时，也不是 FPS |
| 页面数值、CDP 堆 | 页面规模、`Runtime.getHeapUsage` 等 | 帮助解释；不能作为主存或显存总量的替代 |

Chrome 通常由一个 GPU 进程承载多个上下文，但采样程序应发现全部相关 PID，不能硬编码一个。**逐进程显存可能包含跨进程共享资源，简单求和可能重复计数。** 常见单 GPU 进程可直接记录该进程 D/S；多进程时保留明细，并将求和标为可能重复的归属量。整卡适配器计数用于核对，不把有其他会话活动的整卡增量算成作品占用。微软对这种共享计数和引擎汇总方式有明确说明。[微软 GPU 计量说明](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/)

M、D、S 应作为一个资源向量看待，不直接相加成“总内存”，也不把一个 CPU 百分比与一个 GPU 百分比相加。共享图形内存、进程私有提交和驱动资源之间不是简单且无重叠的会计关系。若归属或共享问题足以改变档位，就不要硬判出细微高下。

**一次测量的简化建议**：新建专用 Chrome 和空配置目录，按约定装载及投放后，在连续 10 秒的活动窗口中约每秒采样一次；记录各项中位数和采样最大值。开始加载时即保留资源记录，防止把大额预分配藏在投放前。比较采用同一浏览器的绝对占用，空白页基线仅作解释，不能减去“已加载作品”的基线。允许固定的短准备时间，但预分配不会因此从账上消失。

这是一次短测量，不是十次独立测试。1 Hz 的最大值只能叫“采样峰值”，无法保证抓住所有瞬态分配。没有必要为此上升到复杂的逐分配追踪。计数器无效、PID 已退出或归属不明时标记缺测，不能写成 0；不择优重跑，也不把环境缺测认作作品优秀或作弊。

采样应在一个常驻脚本内进行，不能每个点都重新启动 PowerShell、枚举全机进程或获取堆快照。开始时建立进程归属，运行中补充新 PID；轻量取内存及计数器，窗口外再读取大对象、截图和核实源码。应事先确定投放或扰动的时序，使这 10 秒覆盖活动，不能在活动发生后先等待 10 秒再取读数。本次实验用分阶段命令验证覆盖，并未验证正式 1 Hz 采样器的精度或评分重复性。

直接驱动 Chrome 后，可通过 CDP 设置实际页面视口为 1920×1080、DPR 为 1，并核对内部渲染尺寸及图形后端。单写窗口尺寸不等于核实内容视口；MCP 的截图缩到 1440 宽也不等于实际渲染只有 1440。所有作品使用同样的启动和采样设置，不为某个作品单独开启不封顶出帧、虚拟时间或禁用 GPU。

### 4. 可能的取巧、最少核实办法与可用的短措辞

下面是研究用对照表，不建议整张搬进评分指南。一次评分不必逐行执行；外部计量覆盖常见漏算，源码核实沿着实际发现的疑点追一两条路径。

| 情况 | 最简单的发现办法：看什么代码、读什么数、做什么对照 | 指南可用短措辞 |
|---|---|---|
| 伪造、封顶或美化性能数字 | 查 HUD 数据来源、常量、`Math.min/max`、平滑与取样窗口；与 OS 读数和外部墙钟对照。平滑本身正常，隐藏真实占用或换口径才是问题 | “页面读数只供核实，资源以外部计量为准；检查读数的来源与口径。” |
| 覆盖 `performance.memory`、计时函数或提供假统计对象 | 查 getter、`defineProperty`、对 `performance` / 时钟的赋值；资源改用 OS，时间改用评分进程的单调时钟。隔离世界能减少页面补丁干扰，不能把应用提供的计数变成可信事实 | “不以页面自行提供的接口作为最终测量依据。” |
| 测量时降分辨率、关阴影、改材质、减光路或液体细节 | 查自适应质量、`pixelRatio`、画布尺寸、渲染目标与阴影开关的条件分支；对照投放前后画面和尺寸。按当前可观察效果判断，不凭关键词定罪 | “固定负载中保持选定的完整画面与精度，不以降低要求换取占用。” |
| 显示 N 个物体，只有一部分参与作用 | 沿“投放数量 → 存活状态集合 → 物理更新/GPU 有效范围 → 绘制实例”核实；抽看一个处于群体后部的物体能否被选中并受扰动。不要求一对象一 draw call | “投放数按实际参与作用的存活对象计算，装饰实例和空槽不计。” |
| 固定规模被悄悄截断或超额投放无效 | 查数量输入之后的 clamp、池容量、分配失败分支、循环和 dispatch 范围；对照新增量与存活量，不能只读面板文字 | “指定数量如实进入场景，未实现的数量不算完成。” |
| 用一个代理代表多个会相互独立运动的投放物 | 看是否共享同一状态或只算一个总受力；给其中一个物体施加既有试验台冲量作核实。合法实例化渲染、共享几何并不意味着代理物理 | “投放物保持各自状态及应有作用，不以重复外观充数。” |
| 删掉、冻结已完成环节或视野外对象 | 查节点切换、关卡结束、视锥和屏外判定是否控制物理存活；看对象状态是否仍保留、扰动后是否响应。仅不绘制屏外物体不等于停算 | “节点外和已完成部分仍保持题面要求的作用，不能借测试状态卸除负载。” |
| 用暂停、自然静止或无输入来取得低读数 | 测量窗口覆盖活动过程，查 `paused`、输入事件、`visibilitychange`、焦点和空闲分支；对照实际运动与墙钟。平衡状态不做无效计算属于优化 | “不以暂停、停算或只等静止后的读数代表运行占用。” |
| 把计算搬进 Worker、iframe、OffscreenCanvas 或其他页 | OS 统计整棵专用浏览器进程树；CDP 发现 Worker/子目标/新页；查 Worker 创建、消息返回、状态交换。主线程低占用不能代表全作品 | “计入运行所需的全部浏览器进程和上下文，后台计算不遗漏。” |
| 把计算搬到 Node、本地服务或远端 | 查 `fetch`、WebSocket、网络返回内容和服务端脚本；区分静态文件服务与持续回传物理状态。浏览器树以外的计算不应消失在账外 | “承担仿真工作的外部服务须说明并纳入范围；不得靠转移统计范围获益。”此项授权边界仍需题面明确 |
| 只计 Worker 发消息或 GPU 提交指令的时间 | 查计时终点在 `postMessage` / `submit` 前后，还是对应结果真正完成；核实一次完成回执/同步边界，正式比较看端到端推进 | “异步计算的提交时间不能冒充计算完成耗时。” |
| 多 WebGL 上下文、WebGPU device 或隐藏画布 | 查 `getContext`、OffscreenCanvas、`requestDevice` 和销毁路径；系统按全部相关进程计量。DOM 中画布数量不覆盖 Worker 内上下文 | “计入全部上下文与设备的资源，不只统计主画布。” |
| 在读数开始前预分配；只报投放后的增量 | 计绝对占用，加载开始即留记录，空白浏览器作基线；源码看启动时的大数组、纹理池、缓存 | “加载和预分配的资源同样计入，不以作品加载后的基线抵消。” |
| 虚拟申请大 buffer 冒充规模，或只在未使用时测 | 看是否实际写入、参与更新与绘制，活动窗口覆盖使用阶段；buffer 的声明尺寸不是系统驻留显存。延迟分配本身正常 | “声明容量不等于有效规模，按实际运行的负载核实。” |
| 泄漏、重置残留，或将缓存说成泄漏 | 查每帧 `push`、重复建纹理/上下文、旧节点和 Worker 是否仍被引用；只用本次自然操作中的前后数据辅助。释放后不立即回到初值不足以证明泄漏 | “明显无界增长结合源码判断，不用一次未回落读数断言泄漏。” |
| 检测评测、特定数量或等待若干秒后切换实现 | 查 `webdriver`、headless/UA、DevTools 检测、benchmark 标志、特定 N、按时间或 URL 开关的分支，追到是否改变负载。无需隐藏负载来替代源码核实 | “不以评测识别或固定负载特判改变实际工作或显示。” |

合法优化应当明确受到保护：批绘与实例化、共享资源、对象池、紧凑状态、Worker 并行、GPU 计算、可正确唤醒的静止优化、无画面损失的可见性处理，均不因低占用受怀疑。尺度变大后正确性不变的自适应方法，也不因内部步数或存储方式变化而直接判违规。判断对象是**少做了题面要求的工作没有**，不是使用了哪个技术名词。

一次读数异常只能构成疑点。关键词命中、内存不随 N 线性增长、GPU 利用率低、对象共享网格，都不能单独证明作弊。短测加少量源码阅读无法排除有意设计的所有伪装；本方案的目标是覆盖限时作品常见的统计遗漏和取巧，而不是建立恶意程序的安全隔离系统。

### 5. 不同技术路线怎样公平处理

| 路线 | 容易漏掉的部分 | 公平口径 |
|---|---|---|
| CPU 单线程 | 页面堆之外的数组存储、DOM、渲染进程和驱动资源 | OS 主存和图形内存照常记录；不能因 GPU 计算少而直接加分 |
| Worker | 独立堆、消息副本、共享数组、Worker 在其他进程中的资源 | 整树计量；不对 Worker 数量罚分；墙钟看完成结果，不把并行线程 CPU 时间之和当作单次延迟 |
| WebGL 渲染或计算 | ANGLE/D3D 分配、纹理/缓冲、多个上下文和上传副本 | D、S、M 一起看；JS 堆小不能说明总资源少，调用返回也不代表 GPU 已完成 |
| WebGPU 计算与渲染 | GPUBuffer、设备/队列、异步执行及 CPU/GPU 间的传输 | 同样的可观察结果、相同负载与墙钟；不强制使用与 WebGL 一样的底层后端或数据布局 |

跨路线应比较**达到同一可观察状态的端到端墙钟时间**，不能把主线程函数时间、所有 Worker 的 CPU 时间总和、GPU 时间戳分别放进同一张“物理 ms”排行榜。累计 CPU 时间只作为解释工作移到哪里去了的辅助证据；它可能因有效并行而上升。

如需核实异步计时，可在正式采样之外检查一次 Worker 完成回执、WebGL 完成同步，或 WebGPU `queue.onSubmittedWorkDone()`。WebGPU 的 `submit()` 是提交工作，完成等待覆盖队列此前的工作，可能含渲染，不能冒称纯物理耗时；强制每帧等待又会破坏原有流水并改变性能。[GPUWeb 官方队列说明](https://gpuweb.github.io/types/interfaces/GPUQueue.html)

`--use-angle=d3d11` 不意味着 WebGPU 也被强制为同一个 D3D11 执行路径。应核实硬件加速实际可用、记录后端，避免软件回退混入比较；无需为了形式相同而排除一种题面允许的路线。

### 6. 评分组合与短版指南建议

建议维持“五个方向、总分 100、性能方向 18”，不新增第六个“防作弊”方向，也不另设一串扣分。**若需要一个可落地的分项安排，建议将现有三项合并为“计量可信 3 + 指定负载下的运行与资源 15”。** 合并是为了把“实际做了多少工作”和“为这些工作花了多少资源”放在同一项里，不让少做工作同时被多项惩罚，也不让空场景靠低占用取得资源高分。

- 计量可信：只评所要求的规模、运行状态与读数是否如实、口径是否清楚，不能重复评一次负载能否完成。
- 指定负载下的运行与资源：完成份额看规定负载实际运行了多少；规则看运行中不偷减负载、不降低既定画面与精度、不放慢或停算；质量以完成的有效工作为基础，看 M/D/S 是否处于合理预算、是否有明显浪费。GPU 利用率没有独立分值。

不建议建立 `1/M`、`1/U` 或“内存每少 100 MB 加若干分”的公式。建议提前校准“明显过量、合理、有突出节省且工作等价”的宽档，在测量噪声和质量差异内并档；没有足够依据就不细分。相同资源预算内的 CPU/GPU 转移，不应因其中一个数字下降就获得全部奖励。

物理正确和美术完成情况仍只在原有方向给分。本方向借用已经核实的事实来判断资源是否可比，不重新给物理精度或美术水平打一次质量分。若是只在性能负载触发的减物、降质，则只在本方向处理这一行为。读数造假只归“计量可信”；另项使用外部真实数据继续评价，不因 HUD 造假自动清空全部性能分。原有预计算回放等明确违规，沿用已有处理，不再重复扣分。

可供将来精简进指南的正文如下（需先与题面同步）：

> **计量可信（3 分）**：完成：所需规模和运行数值常驻、口径清楚；规则：读数如实，异步提交不冒充完成；质量：稳定可读，外部核实一致。
>
> **指定负载下的运行与资源（15 分）**：完成：在约定场景、规模和完整画面下正常运行；规则：对象真实参与作用，运行时保持规模、画面和精度，不放慢、停算或转移统计范围；质量：结合实际完成的工作，按外部主存及专用、共享图形内存的合理程度评价。只测一次；GPU 利用率辅助解释，不按其高低给分。缺测不作零占用，已在其他方向评价的物理和画面质量不重复评分。

题面只需要说明规定负载、正常运行的状态、画面保持、规模真实和显示内容；测量口径及不成立时怎样计分写在评分材料。当前题面第七节明确说“资源占用高低不直接决定得分”，2.9 仍要求 FPS 和最长帧时间；因此正式采用新方案时，不能只改指南而留下这些冲突。本文未执行任何修改，也不建议缩减现有十环、节点、参数或三维内容来迁就测量。

## 二、依据与本机实验

### 1. 核对的项目资料及环境

已读取题面、AI 评分指南及两份评分表的相关内容。现行性能为 3/8/7；2.9 要求完整画面和 Worker/GPU 耗时包含，3.2 要求实时推进、不能预计算回放，3.7 要求投放物参与作用且增大规模不降低精度。题面 2.1 第 8 条还要求已完成部分保留作用、节点外继续运行。这些已能支撑多数规模核实，无需再创造复杂的作弊定义。

实验日期为 2026-10-30，约 01:31–01:43，管理员账户。Windows 11 专业版 10.0.26200；Chrome **156.0.8078.48**；RTX 4080；NVIDIA 驱动 **610.88**；Node **24.11.0**。CPU、内存配置沿用出题人给定的 i7-14700KF、64 GB。CDP 返回硬件渲染器为 RTX 4080 的 ANGLE D3D11，WebGL 与 WebGPU 功能启用。

测量权限更正前，曾用 MCP 自建页确认页面 API 可用性；下面用于覆盖范围判断的主要数据均来自**直接启动的独立 Chrome + CDP + PowerShell**。Chrome 使用新配置目录、无窗口、`--use-angle=d3d11 --do-not-de-elevate`，启动窗口 1920×1080、设备比例 1；这些是分配覆盖实验，不进行像素负载比较。

实验没有终止其他会话的进程。只短暂写入几十至几百 MiB 的内存或缓冲并绘制极小三角形，没有持续 GPU 压力测试。每个实验 Chrome 均通过本实例的 CDP 关闭；本地测试服务也只清理自己启动的实例。

**当时有其他受测/研究会话，整机没有独占。以下数据只能验证统计覆盖和计时陷阱，不能用来制定正式的内存预算、GPU 利用率阈值或跨作品排名。** 进程自身的启动、回收、上传副本和缓存也会影响阶段间差值，不应期待每次正好增加声明的分配量。

### 2. nvidia-smi 与 Windows 计数器：哪些量确实能读到

实测命令：

```powershell
nvidia-smi --query-gpu=name,driver_version,memory.used,memory.total,utilization.gpu --format=csv
nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv
Get-Counter '\GPU Process Memory(*)\Dedicated Usage','\GPU Process Memory(*)\Shared Usage'
```

一次整卡结果：`RTX 4080, 610.88, 4029 MiB / 16376 MiB, 4%`。进程列表中的 GPU 内存则为 `[N/A]`，包括 Chrome。Windows `GPU Process Memory`、`GPU Adapter Memory`、`GPU Engine` 均能取得读数。

NVIDIA 官方说明 WDDM 下进程 GPU 内存可能不可提供，因为内存由 Windows 内核驱动管理；整卡 utilization 是采样区间内 GPU 忙的时间比例，不能解读为这件作品利用了多少“有效算力”。所以进程显存不应依赖 nvidia-smi，这台机器应使用 Windows 侧口径。[NVIDIA-SMI 官方文档](https://docs.nvidia.com/deploy/nvidia-smi/index.html)

实验中还遇到过一次全局通配计数器读取报无效数据，脚本随后保留有效样本的 `Status` 并记录错误。正式实现应优先筛选自己的 PID、检查状态；不能将退出的实例、无效样本或 N/A 转成 0。这是采样健壮性问题，不是作品造假证据。

### 3. 主页面读数会漏掉 Worker，单个 JS 堆不是总内存

同一专用 Chrome 中依次执行：空测试页；主页面分配并填充 96 MiB `Uint8Array`；Worker 另外分配并填充 96 MiB，并保持引用。单位 MiB，四舍五入两位。

| 累积状态 | 页面 `performance.memory.usedJSHeapSize` | CDP 页面 `usedSize` | CDP 页面 `backingStorageSize` | 浏览器树私有提交 M |
|---|---:|---:|---:|---:|
| 初始页 | 0.66 | 0.66 | 0.00 | 334.08 |
| 主页面增加 96 MiB | 96.45 | 0.45 | 96.00 | 441.08 |
| Worker 再增加 96 MiB | 96.47 | 0.47 | 96.00 | 525.04 |

新增 Worker 数据后，主页面读数仅变约 **0.02 MiB**，浏览器树私有提交增加约 **83.96 MiB**。主页面 `usedSize` 从未接近这两块数据的总量。这里没有改写任何读数，单纯换个执行位置就足以使页面统计漏算。

CDP 官方将 `getHeapUsage` 定义为对应 isolate 的统计，并分别提供 JS 堆、embedder 堆和数组等的 backing storage；它没有承诺把全部 Worker、浏览器原生资源和 GPU 存储合成一个总量。[CDP Runtime 协议定义](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/js_protocol.pdl)

### 4. SharedArrayBuffer：连主页面的数组数据也不一定进入同一口径

另一个新 Chrome，测试服务为该页启用 COOP/COEP；在主页面创建并填充 96 MiB `SharedArrayBuffer`，然后让 Worker 引用同一块内存，未复制第二块。

| 累积状态 | 页面 `usedJSHeapSize` | CDP 页面 `backingStorageSize` | 浏览器树私有提交 M | 工作集之和 W |
|---|---:|---:|---:|---:|
| 初始页 | 0.48 | 0.00 | 290.81 | 559.54 |
| 写入共享数组 96 MiB | 0.49 | 0.00 | 376.84 | 647.46 |
| Worker 引用同一数组 | 0.51 | 0.00 | 384.49 | 651.70 |

这次页面和该 CDP backing 指标都没有呈现这 96 MiB；OS 的私有提交和工作集则明显增加。同一块共享数组交给 Worker 后，也没有再增加 96 MiB。不能按 API 声明长度逐份相加，更不能认为任何一个“JS 内存”字段都包含所有数组。

普通 localhost 页中 `measureUserAgentSpecificMemory` 为 `undefined`；启用隔离后为 `function`。本实验没有将它的返回值当作总资源基准。Chrome 团队说明该 API 有隔离要求、统计依赖实现，且可能排除部分区域；单次结果也受事件和回收时机影响。[Chrome 团队关于页面内存 API 的说明](https://web.dev/articles/monitor-total-page-memory-usage)

评分 AI 可以控制启动参数和服务头，不代表必须用这个 API；为计量临时加隔离头可能改变跨源资源加载。优先用系统侧读数，不要求作品为测量更改部署。

### 5. 多上下文显存：外部统计可以覆盖，但申请与使用要分清

独立 Chrome 中，先创建一个 WebGL2 上下文，为其 32 MiB 顶点缓冲写入数据并实际绘制一个 64×64 画布内的小三角形，再对第二个上下文做同样操作；两次 `getError()` 都为 0。系统中由同一 GPU 进程承载。

| 状态 | 浏览器树 M | GPU 进程专用 D | GPU 进程共享 S |
|---|---:|---:|---:|
| 初始页 | 325.33 | 46.40 | 3.26 |
| 一个上下文，使用 32 MiB 缓冲 | 450.30 | 78.79 | 34.66 |
| 两个上下文，各使用 32 MiB 缓冲 | 484.72 | 108.54 | 66.69 |
| 删除缓冲并丢失上下文后短时读数 | 450.90 | 108.29 | 34.78 |

系统显存能看到多个上下文累计的占用。删除后专用显存并未立刻恢复初始值，所以“一次重置后显存没有降回去”不足以断言泄漏。

较早的试验只写入 WebGL buffer、清屏，没有让 buffer 真正参与 draw；两块共 64 MiB 的声明缓冲并未让专用显存相应增加。补上实际绘制以后才得到上表。因此应把**被实际执行的工作**作为负载，不能把 `bufferData` 的大小当作已占用物理显存。这也是不能只审核申请容量的实验依据。

另一次累计分配试验中，WebGPU 创建 32 MiB storage buffer、写入并等待队列完成后，GPU 进程 D 从 **46.40** 增到 **98.68 MiB**，S 从 **2.77** 增到 **31.76 MiB**。变化包含实现开销和先前状态，不能按 32 MiB 精确归因；它至少证明 WebGPU 资源能被同一 Windows 系统计量路线观察到，无需靠页面编造显存总数。

### 6. 异步提交的 0 ms 不等于计算 0 ms

创建一个 Worker，接到消息后执行约 120 ms 的计算，再回复完成。用主页面计时：

| 测量边界 | 结果 |
|---|---:|
| 只包住 `postMessage()` | **0.0 ms**（本次计时精度下） |
| 从发送到收到完成回复 | **123.7 ms** |
| Worker 内部实际执行区间 | **120.0 ms** |

这是对“后台计算不覆盖”的直接复现。页面可以完全无恶意、却给出虚假的低耗时；看源码确认计时边界，比要求评分 AI 修补每一种实现的计时器更简单。正式资源测试无须修作品源码，改用外部统计即可。

### 7. 整机差分的污染与实验复查位置

共享数组试验的三个阶段中，整机 `Committed Bytes` 为 **47148.25 → 49047.17 → 55289.02 MiB**。本测试只增加一块 96 MiB 共享数组和一个引用它的 Worker，无法把这些整机变化归因于本页。它与本机当时并非独占的事实一致，也说明当前数据不能校准阈值。

正式评分即使独占性能题，仍有桌面、浏览器服务和驱动缓存；优先使用专用浏览器的归属数据，整卡/整机量用于核对。若归属读数失效而只能依赖受污染的全机差分，资源部分应记测量不足，不能用减一张空白页的整卡截图补成精确成绩。

## 三、需要出题人拍板的问题

1. **“GPU 占用”指什么？** 建议正式采用专用及共享图形内存预算；GPU 利用率只记录不计分。若坚持给利用率分，就要接受无法充分消除画面、出帧节奏和 CPU/GPU 分工偏差。
2. **选定哪份公开负载？** 是否采用第 9 环及候选 256 个混合投放物？数量、尺寸、物性、位置/间距、批次、初态和测量区间需要在题面定死，不能由评分 AI 临时各挑一份。
3. **输出等价做到多严格？** 沿用现有现象和画面要求，就按宽档评价；若希望按内存数字细排，需要补充可观察的精度/细节约定，仍不指定实现。
4. **性能 18 分怎样改？** 建议“计量可信 3 + 指定负载下运行与资源 15”，把负载完成与资源质量合在一项，GPU 利用率不另设分。不再保留“帧率平稳”和逐步探最大规模的隐性测试。
5. **内存预算和档位在哪里？** 本次只验证可测性，不能给出有根据的 MB 阈值。需用代表性的完整实现做一次出题校准，再固定宽档，避免临场按作品之间最低值定标准。
6. **实时容差与单次窗口如何定？** 建议一次 10 秒活动采样，外部墙钟核实真实推进；正常速度允许的误差，以及缺测时如何给出非数值判断，应预先统一。
7. **本地服务和远端计算的边界？** 现行题面允许 JavaScript、Worker 与 GPU，但未明确测量范围外的仿真服务。建议题面说明作品在本机网页环境完成所需计算；纯静态开发服务正常，承担仿真计算的进程不能在账外。禁止或计入二选一，不能测完临时加规则。
8. **是否接受精度有限的外部占用口径？** 建议接受 M/D/S 的归属与共享限制，细微差异并档，异常缺测不当零占用；不要承诺一次短测能证明无泄漏、无所有隐藏分支，或给出精确的跨技术路线总内存。
