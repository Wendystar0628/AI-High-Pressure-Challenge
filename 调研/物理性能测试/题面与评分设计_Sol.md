# 《一道光谱》仿真性能：题面与评分设计建议

调研日期：2026-10-30。已通读现行题面、AI 评分指南及两份评分表；两份评分表除评分员名称外，正文相同。本报告只提出替换建议，未修改这些文件。

**前提以出题人的最新更正为准：评分 AI 在管理员账户下直接启动本机无窗口 Chrome，可以自定启动参数、用脚本或 CDP 驱动，并运行 Windows 计数器和命令行。受测模型开发时使用的浏览器 MCP，不限制评分端的测量能力。**

## 一、结论与建议

1. **取消帧率评分是可行的，但资源占用不能直接接替帧率成为“越低越好”的排名。**应先固定要完成的工作，再看完成这些工作用了多少资源。否则少做水体、碰撞、阴影、反作用的作品天然占优。
2. **把“GPU 占用”拆开。**GPU 专用内存、共享内存可以作为资源预算指标；GPU 利用率只记录，暂不计分。利用率与出图频度、可见像素、材质效果、CPU/GPU 分工有关。即使直接驱动 Chrome，也不能由一个百分比推出实现优劣。GPU 计算较多也可能是合理地分担 CPU 工作。
3. **用一个固定的第 9 环试验场景，测一次 10 秒。**完整机关运行到目标达成，保持当时状态，在晨池上方一次投入 256 个四种材料的方块，使用明确的“基准精细档”和完整画质。只采这一段资源，不测全程 FPS、不找卡顿点、不长时间跑、不逐级试到崩溃。
4. **建议保留性能方向 18 分，改为“读数与实时真实性 3 分＋基准规模与资源 15 分”。**原来的 8 分与 7 分合并，避免“少放对象”同时在规模项和资源项各扣一次，又避免把减物后的低占用当成优化。其余四个方向及分值保持 14／26／24／18，总分仍为 100，仍是五个方向。这样总分项数由 24 变为 23，今后同步模板及结果结构时应一并更新；本次未改。
5. **删除“测得节点规模上限”的说法。**本方案证明的是“在给定内容、精细度和资源预算下兑现了多少统一负载”，不是作品真正的最大容量。只测一次固定负载，无法诚实地得到最大容量。试验台仍允许继续加大数量和精细程度，不能凭输入框标出的上限加分。
6. **资源由评分端外测，作品不必显示本机总内存或 GPU 利用率。**作品常驻显示仿真时间、正常播放经过的真实时间、实际物体数、实际生效的精细档与画质状态；资源报告由评分脚本产生。网页里的 JS 堆不能冒充网页总内存，不支持的读数应明确写“不可用”。

以下给出具体场景、计分锚点和可直接替换的文字。**256 个对象、4 cm 方块、细节标准及资源阈值是设计建议；本次小实验验证了测量通路，没有用完整参赛作品标定难度或优秀开销。不能把文中的试行数值称为实证最优阈值。**

## 二、固定规模应当固定哪些东西

### 2.1 推荐的唯一正式基准

| 项目 | 统一规定 |
|---|---|
| 原有机关 | 保留全部十环、展厅、水体、绳簧和光路；完成作用的对象继续留在场景中，仍能响应相互作用 |
| 初始状态 | 默认物理参数，其中重力为 9.8 m/s²、水密度为 1000 kg/m³；正常速度，从敲击运行到水晶累计受光约 1.5 秒、目标首次达成的时刻，暂停。打开第 9 环节点，保持这一刻的状态，不退回第 9 环开头 |
| 投放对象 | 木块、冰块、砖块、黄铜块各 64 个，共 256 个；均为边长 0.04 m 的立方体。质量依次为 0.032、0.0576、0.128、0.544 kg，分别对应密度 500、900、2000、8500 kg/m³ |
| 投放位置 | 晨池中部预留一块至少 0.48 m × 0.48 m 的无遮挡水面。以其中心为原点，沿池的长、宽方向排 8 × 8 列，共四层；中心间距均为 0.06 m；最下层中心高出暂停时的水面 0.14 m。没有实体投放架，不增加挡墙或固定物 |
| 材料排列 | 各层各材料各 16 个，按木、冰、砖、黄铜循环排列；用层号、行号、列号之和除以 4 的余数确定材料。每次相同，不随机抽取 |
| 初速度与朝向 | 初速度、角速度均为零，各面沿池的长、宽和竖直方向；投放时不互相重叠、不嵌入装置 |
| 精细程度 | 统一选“基准”档；其含义见下一小节。更高档仍可提供，但本次不改档 |
| 画质与声音 | 使用完整的基准画质：题面要求的材质、玻璃与水的透明及折射、软影与晨光硬影、接触暗部、光束、光谱、反馈和界面均保留；每个投放物有对应材质和影子。声音保持正常启用及默认音量 |
| 辅助显示与面板 | 辅助显示打开，采用第 9 环默认显示；节点卡、记纹鼓、试验台和性能读数保留，参数面板收起；不得进入只画负载物的简化场景 |
| 镜头与分辨率 | 第 9 环的固定基准机位，不自动跟随或移动；能同时看到投放区、吊桶和浮镜筏。CSS 视口 1920 × 1080，设备像素比 1，主三维画面内部输出 1920 × 1080，不先低分辨率绘制再放大 |
| 计量窗口 | 布置完成后继续正常播放，同时外测 10 秒；投入的对象全程保留，运动和作用由仿真继续推进。试验改变光路或使连锁停下属于试验结果，不要求再达成一次目标 |

选第 9 环，是因为已有的试验台、浮沉材料、吊桶入水、波纹推物、绳簧联动和光路都能用上，不需要另造一套与题目无关的压力测试。四种材料合计体积约 16.38 L、质量约 48.74 kg，全部真正入水时是明显扰动，不应事后把它调轻以保证机关继续成功。

这里固定的是**输入和要呈现的现象**，并不要求各作品的液体、绳索内部用同一种表示。同样叫“1 万个单元”，不同表示承担的工作可能不同，不宜拿内部单元数当跨作品的统一规模。

预留投放区是为让各作品都能放入同一批物体，不能让评分 AI 每次自行找位置、改尺寸或避开难算区域。具体机位可以由各作品根据自身布局提供，不要求统一相机矩阵；因此这仍是同题作品的粗粒度资源评价，达不到同一个标准渲染器的像素级可比性。

### 2.2 “基准精细档”应当按结果定义

只写“取高档”没有意义：一个作品的高档可能比另一个作品的低档还粗。也不宜规定液体必须有多少粒子、网格或绳段，这会把实现手段写进题面。

建议把原有精细度控件改成至少有一个名称固定的“基准”档，其可观察要求为：

- 水面能区分相隔 0.04 m 的两处入水扰动及其传播；投放物与水体的交界、浮沉和波纹推物可辨，不合并成整池同步起伏。
- 绳、链的松弛和弯曲在约 0.02 m 的局部尺度上仍可辨；松紧、轮槽与连接关系保留。这里只规定外观和作用，不规定分段方式。
- 最终光路至少同时计算 21 条入射光线，七个色区各不少于三条，分别沿当时的完整光路传播；反射、折射后的多段不能重复算作新的入射光线。光束和墙面光谱仍按原题呈连续效果。
- 基准档覆盖场景中的全部相关水体、绳链和光路，不只提高当前镜头前的局部细节；进入节点不改变其余部分实际生效的精细程度。

这些是拟议的最低可辨细节，**不是已经做过收敛验证的精度标准**。正式采用前应在至少一件完整作品上确认：1920 × 1080 的基准机位下，4 cm 扰动和 2 cm 绳链细节能被看清。视觉上无法核验的数字不要装成严格量化精度。

“画质完整”也不等于把作者所有可选特效都开到最高。应固定满足 2.6 的基准画质；额外超采样、额外装饰等可以有更高档，但不进入资源比较。基准档已有的效果不可在测量时临时关闭。

### 2.3 作品内要显示什么

常驻部分尽量短：仿真时间、正常播放累计真实时间与倍率；全场实际刚体数及其中的本次投放数；当前实际生效的精细档、画质档和主画面内部输出尺寸。暂停、慢放、快速推进应明确区分，不能把暂停时长混进正常播放对照。

可展开详情：四种材料各自的存量，液体、绳链精细程度的说明和实际工作规模，实际入射光线数。不同表示可以用各自有名称的工作单位如实说明，不强迫单位统一，也不按单位数量直接评分。不得把“申请投放 256 个”当成“实际还在场 256 个”，不得只显示控件目标值。

不再强制帧率、最长帧时间或“每帧物理耗时”。异步 Worker／GPU 的耗时很容易被误写成提交耗时；既然不评流畅度，没有必要把这项复杂读数继续设为硬要求。作者可自愿显示，但必须标清范围和来源。

## 三、测量与评分设计

### 3.1 评分端测量口径

评分 AI 为该作品启动独立 Chrome，使用独立临时用户目录、单一被测页面，固定 Chrome 版本、D3D11、视口和像素比，不加入调低画质、软件渲染或关闭显卡的参数。用 CDP 验证实际视口、像素比和 GPU 后端；仅有 `--window-size` 不作为内部画面尺寸的证明。正式测量期间不截屏、不跑追踪、不抓堆快照、不强制 GC，也不改受测作品的仿真或渲染代码。

| 量 | 采集及汇总口径 | 用途 |
|---|---|---|
| M：私有提交内存 | 由自己启动的 Chrome 根 PID 及其动态进程树，读取每个进程的 Private Bytes／PrivateMemorySize64；含浏览器、渲染器、GPU、工具进程及 Worker 所在进程。先对同一时刻求和，再取十秒窗口中 1 Hz 采样的最大值 | 主要资源指标；不是物理驻留内存或 JS 堆 |
| D：GPU 专用内存 | Windows `GPU Process Memory` 中，该独立 Chrome 的 GPU 进程、RTX 4080 对应实例的 `Dedicated Usage`；同窗口取采样最大值 | 显存预算指标 |
| S：GPU 共享内存 | 与 D 相同实例的 `Shared Usage`，同窗口取采样最大值 | 单列预算，避免只压低专用显存而把开销挪入系统共享内存 |
| U：GPU 利用率 | `GPU Engine` 按 GPU PID、适配器及具体引擎读取，保留 3D、Compute、Copy 等引擎信息；摘要可列每次采样的最忙引擎，再报窗口平均和最大值 | 只作解释，不决定分档；不把各引擎百分比相加 |
| 时间与规模 | 用外部单调时钟对照仿真时间增量；核实实际投放数、生效精细档及内部输出尺寸 | 真实性和负载有效性 |

M 是可重复取得的“私有提交”口径，不应在报告里简称为进程树实际占用的物理 RAM。也不要把 M＋D＋S 相加称作总内存：共享、映射和驱动记账会产生交叉。Windows 进程显存本身包含跨进程共享资源，也不能再把 GPU 进程与渲染器报告的显存相加。

正式统一采集器应先确认该 Chrome／WebGL 或 WebGPU 路径的图形资源能由上述 GPU 进程实例覆盖。如果出现多 GPU 进程、主要资源归属不明或计数器异常，**不要为某一作品临时挑一个更好看的口径**。可在开赛前统一改用 RTX 4080 的设备级专用／共享内存相对同一独立浏览器空白页的增量，结合 PID 读数核对归属；所有作品统一使用该口径。设备级读数会混入桌面与后台开销，必须配粗档，不能比较几十 MiB 的差距。

一次十秒内取十个左右采样，不是反复试验；记录的是“1 Hz 采样最大值”，不是任意瞬间的真实峰值。保留原始记录即可。前面跑完连锁属于原有内容评审和建立初态，不另做一场性能耐久测试。两位评分员使用同一份资源记录，分别裁决内容和质量，不再各跑一次导致机器状态不同。

若评分端计数器失败，这是测量问题，不能记成作品读数为零、优秀低占用或作品缺功能。若无法在统一口径下取得可信资源结果，保留负载完成判断，资源质量暂用普通档并注明未实测，不宣称省资源；不为凑数改作品。这与作品自己伪造读数是两件事。

### 3.2 分项与分档

建议维持性能方向 18 分，但合并旧的规模、精细和资源关系：

| 新分项 | 分值 | 完成 | 规则 | 质量 |
|---|---:|---|---|---|
| 读数与实时真实性 | 3 | 常驻时间、实际规模、生效档位和输出尺寸；正常速度下状态持续实时推进 | 读数来自实际状态和测量，不以目标值、常量、随机数代替；不虚增仿真时间 | 与外测相符、稳定易读；普通完整约 0.5，清楚准确且可核验为 1 |
| 基准规模与资源 | 15 | 第 9 环基准投放和精细档可实际运行；投入对象保留并参与作用，实际承载数量计入完成份额 | 统一画质与精细程度，不通过减物、冻结、漏算或降档节约开销 | 对等价负载看外测 M、D、S 的粗档；不按 GPU 利用率、FPS、方法名称或自报上限加分 |

仍用“得分＝分值×完成份额×做得多好”。基准项的完成份额主要反映这批新增负载真正兑现多少，例如四种材料各投入 32 个并真实参与，相应规模约完成一半；只画 256 个外壳、只有少数参与作用，按实际承载估计，不能按宣称数算。

**现有内容的归属不变：**液体算得准不准归物理正确，材质精不精致归画面，试验台是否好用归界面；性能项不再重评美术和物理水准。数值造假只在“读数与实时真实性”体现；实际减少新增负载或自动降档，只在“基准规模与资源”的完成或规则中体现，同一事实不再分别扣两项，也不对完成份额与质量各扣一次。

**资源优化奖励必须有等价负载证据。**场景严重缺环、少了水体或必需画面效果时，仍在原归属分项评价缺做；不得因为这种缺做得到的低资源数，把性能质量判为优秀。无法形成等价比较时，资源质量采用普通档 0.5，明确写“不可比较，未授节约奖励”，不再按其他方向少得的分数乘一个惩罚系数。新增基准对象缺失则只降低本项完成份额，已有部分未形成可比开销时同样采用普通档，不再因数量少另压一次质量。

这个边界不能保证任何缺做作品的性能分都低于任何完整作品——完整但极浪费资源的实现也可能性能差。它能保证“少做所以占用低”不会直接换来资源优秀档；作品的整体好坏仍由其余 82 分承担。若另设“画面低于某分，性能全零”，就破坏了一事只在一项评价的规则，不建议采用。

这里需要明确“证据资格”的解释：原内容缺项只在原项计其缺分，性能不据不等价的低占用证据授优秀档，也不再追加跨项惩罚。如果把“不授资源优秀档”也视作同一缺项影响两处，则“严格禁止任何跨项影响”和“缺做不能获得低占用奖励”存在冲突。建议事先认可这种资格边界，不让评分员临场决定。

#### 可试行的数字锚点

为了使建议具体，给出一套**待完整作品标定**的粗档。基准预算暂取 M＝2 GiB、D＝2 GiB、S＝0.5 GiB，令：

`R = max(M / 2 GiB, D / 2 GiB, S / 0.5 GiB)`。

| R | 做得多好 | 含义 |
|---:|---:|---|
| ≤ 0.25 | 1.0 | 相同负载下三项资源都有很大余量 |
| > 0.25 且 ≤ 0.5 | 0.75 | 明显节省 |
| > 0.5 且 ≤ 1 | 0.5 | 普通完整档 |
| > 1 且 ≤ 2 | 0.25 | 开销偏大 |
| > 2 | 0.1 | 开销明显失衡 |

边界附近允许按相邻档过渡，不因几 MiB 的差异跃变。预算内越小也不无限加分；不以最低占用作品作为全场满分基准。这样后加入一个偷工减料的低占用作品，不会改变其他人的分数。

这组预算相当于一个可公开的初稿，不是由下文的空网页实验推导出的优秀实现开销。开赛前应用完整作品确认后锁定；若不做这一步，宁可用“普通、明显节省、明显浪费”的粗档并附证据，也不要发布看似精确的硬阈值。若改为相对锚点，应以赛前固定的完整参考作品开销为基准，不用当场所有提交的最小值、百分位或主观名次。

### 3.3 如何防止测量时降低工作量

- 测量只使用普通播放、节点和试验台已有的功能。可以提供一键布置基准，减少输入差错，但它只能设置同样的参数、投放物、档位和机位，随后走普通仿真；不能另有一套“基准运行结果”。
- 固定的是实际生效状态。档位标签没变而内部降低精细程度、主画面悄悄降分辨率、停算画外节点或已完成对象，同样改变了负载。原有静止对象可以省去不必要工作，但仍必须能立即响应新的受力和接触；不要求无意义地对静止物重复计算。
- 窗口前核对尺寸、档位、对象数；窗口后结合画面和源码抽查一两处对象真实参与、资源自适应和时间推进的关键路径。无需把正式指南写成长测试清单。对象是否真参与不能只信作品自己的计数器。
- “不跳步”应禁止的是丢弃应推进的物理时间、跳过必要作用或只改时间显示，不是强制每帧恰好计算一步，更不是禁止任何合法的时间推进方法。正常速度下卡慢应如实暴露，不能用未推进的状态配一个走得很快的时钟。
- 不要求防住任意恶意程序或提供安全级反作弊证明。短窗口、外部计量和简短源码核实能发现常见规避，不能证明作品在所有未测时刻都没有特殊分支；评分材料应如实承认这一限制。

## 五、依据与本机小实验

### 5.1 现行文件为什么需要一起改

- 2.9 以“运行流畅”为规模和精细程度的前提，要求 FPS、每帧物理耗时及最长帧时间；3.2 第 2 条只禁止为了维持帧率而放慢；3.7 只简述规模真实。直接替换一个指标名称，会留下“流畅到什么程度算最大规模”的空缺。

- 第七节性能说明、评分指南的方向边界、分项总数，以及两份评分表今后需同步。只改 2.9 或只改指南都会前后不一致。本次仅写本报告。

### 5.2 实验条件与结果

实验全部放在本报告作者的工作目录，没有把网页、脚本、浏览器用户目录或原始数据写入项目。只关闭自己创建的测试页及自己启动的 Chrome，没有结束其他会话的进程；没有跑持续 GPU 重负载。

实机读取：Windows 11 专业版 10.0.26200；Chrome 156.0.8078.48；RTX 4080，驱动 610.88，`nvidia-smi` 报总显存 16376 MiB。已读取浏览器 MCP 配置，确认版本 1.12.0 及 `--headless`、1920 × 1080、`--use-angle=d3d11`；这些只用于核对开发环境。正式方案以评分 AI 直接启动 Chrome 为准。

**实验 A：经已有 MCP 打开自建测试页，验证页面内读数的局限。**

- 页面实际 CSS 视口 1920 × 1080、DPR 1，WebGL 返回 RTX 4080／ANGLE／Direct3D11。
- 主页面申请并写满 64 MiB TypedArray，再让 Worker 申请并写满 96 MiB。被识别出的对应 Chrome 分支，私有提交合计从 356.36 MiB 增至 516.90 MiB；但页面 `performance.memory.usedJSHeapSize` 前后都是粗化的 10,000,000 字节。
- 随后申请并清除写入八张 2048 × 2048 RGBA8 纹理，名义容量 128 MiB。GPU 进程专用计数器从约 147.95 MiB 增到 264.97 MiB，两次相邻采样相同；GPU 引擎当时已闲下来，利用率为 0。

**实验 B：独立启动 Chrome，直接 CDP 驱动，同步命令行外测。**

使用独立临时用户目录，`--headless=new --use-angle=d3d11 --do-not-de-elevate --force-device-scale-factor=1 --remote-debugging-port=0`；另开 `--enable-precise-memory-info` 只是为了观察页面堆读数，正式外测不依赖它。用 CDP 指定实际 1920 × 1080、DPR 1，确认渲染器是 RTX 4080 D3D11；通过 `SystemInfo.getProcessInfo` 取得本浏览器进程信息，Windows 计数器按自己的 GPU PID 读取。

| 阶段 | 进程树私有提交 MiB | GPU 进程专用 MiB | GPU 进程共享 MiB | 主页面 JS 堆字节 |
|---|---:|---:|---:|---:|
| 初始测试页，WebGL 已初始化 | 399.93 | 129.29 | 3.11 | 977,694 |
| 主页面 64 MiB＋Worker 96 MiB 已写入 | 575.41 | 129.29 | 3.11 | 67,799,989 |

- `resource_probe.html`、`resource_snapshot.ps1`、`baseline.json`、`cpu_alloc.json`、`gpu_alloc.json`：实验 A。

### 5.3 官方资料对口径的约束

- Chrome 团队说明，旧的 `performance.memory` 是 JS 堆口径，可能任意偏离页面实际内存；较新的 `measureUserAgentSpecificMemory()` 需要跨源隔离，还可能等待 GC。本次普通本地页面 `crossOriginIsolated` 为 false，该方法为 undefined。因此不把这种页面 API 设成总资源计分入口。[Chrome 团队：页面总内存测量](https://web.dev/articles/monitor-total-page-memory-usage)
- NVIDIA 明确说明，WDDM 下进程 GPU 内存不可由 `nvidia-smi` 正常提供；`utilization.memory` 表示采样期内设备内存读写活跃的时间比例，不是显存容量占用率。[NVIDIA nvidia-smi 文档](https://docs.nvidia.com/deploy/nvidia-smi/)
- Microsoft 说明，任务管理器的 GPU 综合利用率取最忙引擎；跨进程共享的图形资源会在各进程显存中重复出现，所以不能相加得总显存。[Microsoft：任务管理器中的 GPU](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/)
- Microsoft 另记录过 Windows 10 某些情形下进程显存计数异常的已知问题。这不能推出当前 Windows 11 一定有该问题，但足以说明不应把一条进程计数器当成逐字节真值，也不应拿其微小差异排名。[Microsoft：GPU 进程内存计数异常](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/gpu-process-memory-counters-report-wrong-value)

### 5.4 为什么直接驱动 Chrome 仍不能让 GPU 百分比成为主分数

直接驱动解决了浏览器隔离、参数控制、采集权限的问题，没有自动解决等工作量问题。相同 256 个物体，一件作品可能让液体、透明、软影和光谱更复杂；另一件把大量仿真放在 CPU 上。GPU 百分比低可能分别意味着节省、少出图、CPU 限制、少做效果，或者数据采样时已停下来。

若强行计 GPU 利用率，就还要固定实际提交的画面数量、相机与可见像素、着色效果，并核对没有少画；或者改测完成相同工作的 GPU 时间。前者重新引入出帧验证，后者引入跨后端 GPU 计时和仪器开销，都已超出“一次、简短、不同作品自由实现”的当前边界。增加启动参数本身不能消除这些区别。因此本方案测 GPU 利用率但不给它低占用奖励，GPU 内存只按粗预算与 RAM 一起评价。

## 六、需要出题人拍板的问题

1. **是否接受“GPU 内存计入资源，GPU 利用率仅旁证”？**推荐接受。若 GPU 百分比必须直接换分，需要另行统一出图工作量，不能沿用本稿声称已经可比。
2. **是否采用 18＝3＋15 的两分项？**推荐采用，规模和资源在同一项内结合；相应总分项数为 23。若坚持保留三个性能分项，必须先拆清规模缺失与资源资格的归属，不能沿用原 3／8／7 三项各扣一遍。
3. **是否采用这一个 256 物体、4 cm、四材料的第 9 环场景及“基准”精细档？**推荐先保留该规模，在完整作品上做出题前校验；确认投放区容得下、扰动有意义、细节看得清。需要调整就全体统一调整，正式评分不因作品弱而减数量。
4. **资源预算是否先试行 M 2 GiB／D 2 GiB／S 0.5 GiB，还是先用完整参考作品锁定锚点？**推荐先用完整作品标定再锁定。空网页实验只能证明测得到，不能证明哪个数对应普通、优秀。
5. **是否接受不再测“真正上限”？**推荐把名称改为本稿的“基准规模与资源”，只声称验证统一负载；界面仍能继续加大数量。若要真的给最大容量排位，需要额外的递增试探和成功标准，与这次只测一次固定规模的要求不兼容。
6. **是否认可等价负载属于资源优秀档的证据资格？**推荐认可，原内容缺项仍只在原项计缺分，性能不追加跨项扣分。若连“无效低占用不能获优秀档”也算重复影响，需要先调整这一规则，否则与防止偷工减料获奖无法同时严格满足。

以上问题是出题与权重选择，不是要求评分时再逐作品征求确认。锁定后，评分端按同一场景、同一采集器和同一档位一次执行。
