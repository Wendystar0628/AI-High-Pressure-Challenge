### 1. 样例几乎校验不了公式｜已验证｜建议开跑前改

- **在哪**：题面 `:200-217`（第五节）、`:153-162`（第四节）；`grader.cu:75-84, 95-100`；`gen_hidden.cpp:64-74, 330-334`。
- **问题**：样例 $D=2$。最后一步 LN 对两维 token 算出的是 $\pm\delta/\sqrt{\delta^2+10^{-5}}$，只要两维之差不是极小就约等于 $\pm1$，所以 $y\approx\pm\gamma+\beta$。6 个输出实际只含 3 个符号位，前面算得对不对基本看不出来。
- **依据**：`sample_mut.py`、`sample_new.py` 用独立的 numpy 实现测了 19 种常见写错，在评测程序的容差下：
  - 现样例只查出 5 种：`W_O` 转置、注意力残差漏 `x`、g 换 ReLU、FFN 置零、漏最后的 LN。
  - 漏掉 14 种：交换 $W_Q/W_K$、去掉因果掩码、因果差一位、漏 $\sqrt d$、注意力整个置零、漏 $Q/K/V$ 的偏置、$V$ 用错权重、$W$ 转置、各头拼回顺序反、不分头、$g(t)=t$、$\Phi$ 换 tanh、方差除以 $D-1$、第二步 LN 用错参数。
  - 完全不算任何层、只对原始 $x$ 做最后的 LN，也能通过。最后 LN 之前的状态完全随机时，通过率是 11.8%。
- **影响**：样例是模型手里唯一的官方对照。第十一节让模型和“简单可靠的实现”核对，但这个简单实现如果读错了公式，样例查不出来。隐藏正确性输入能查出（我试的 5 种错误，凡是在该输入上起作用的都超容差 24–546 倍），结果是 $k$ 接近 0、性能输入全错，整题约 0 分。这种情况概率不高，但后果最重，修复又便宜。
- **建议**：换成 $B=1,S=3,D=4,H=2,F=2,L=1$ 的样例，19 种全部查出，查出最弱的一种也超容差 53 倍；只做最后 LN 不再通过。基线和我的简单解都通过（`tolerance_ratio` 0.0004、0.0001）。需要同步改题面第四、五节、`grader.cu`、`gen_hidden.cpp`（数组长度 126/12/12，`sample{1,3,4,2,2,1,...}`，循环到 12）。不影响隐藏输入和答案。数据如下（`调研\Transformer题审查\实验\Opus\sample_D4.txt` 有同样内容）：

### 2. 受测解触发 TDR 时，脚本会连续重复触发，可能牵连基线甚至蓝屏｜推断（共享 GPU，未实际触发）

- **在哪**：`evaluate.py:149-153, 197-208, 221-222`；题面 `:287`。
- **问题**：
  - 受测解在某输入上失败后，脚本仍跑完该输入的 3 次，尽管这个输入已确定 0 分。
  - 超长输入 p10–p12 连在一起，都是 `C/R` 交错。不切分提交的解在每次受测运行的第一次 `forward()`（未计时的那次）就可能触发 TDR。
  - 粗估受测解失败一次约 5 秒，基线 p11 约 6 秒、p12 约 9 秒。按 `R C C R R C`（p11）接 `C R R C C R`（p12）的顺序，这两个输入的 6 次受测运行落在约 55–60 秒内。
  - 本机注册表没有 Tdr 覆盖项，按微软文档的默认值（`TdrLimitCount=5`、`TdrLimitTime=60`），60 秒内超过 5 次会蓝屏。这个估算正好卡在上限附近。
  - 另外每个输入都有一次基线紧跟在受测运行之后。如果碰上驱动恢复期失败，整场 `score=null`，重测还可能再来一遍。
- **影响**：只在受测解不听题面警告、单次提交过长时才发生，概率不高。真发生时最坏是无人值守的评分中断。
- **建议**：两处小改，约 5 行。受测解在某输入首次失败就跳过该输入剩余的受测运行；基线失败时等 15 秒重试一次，再判作废。不影响正常提交的计分。

### 3. 第九节第 4 条字面上会把错误路径的打印判成整题 0 分｜已验证（读文件）

- **在哪**：题面 `:267`；`AI评分指南.md:27`；`grader.cu:22-32`；`reference_solution.cu:35-40`。
- **问题**：规则写“不能使用标准错误”，指南写违反记 0 分。但只在 CUDA 出错时才执行的 `fprintf(stderr, ...)` 是常规写法：题面给的评测程序和基线都这样写，模型很可能照抄。
- **影响**：严格按字面评就是整题 0 分，放不放过取决于评分员。用户可以手动改分，所以代价不大。
- **建议**：第 4 条和指南加半句：“正常运行时不向标准输出、标准错误写内容；出错退出前打印诊断信息不算违规。”

### 4. 解法向标准输出写入非 4 倍数字节时，`evaluate.py` 整个崩溃｜已验证

- **在哪**：`evaluate.py:49-51`。
- **问题**：`np.frombuffer` 在长度核对之前执行，抛 `ValueError: buffer size must be a multiple of element size`，整场中断；第一个正确性输入就崩的话，连报告文件都不会生成。空输出和长度差 4 倍数字节的输出都能正常判错，只有这一种情况会崩。
- **影响**：这种提交按规则本来就是 0 分，只是让评分员多走一步。
- **建议**：先判长度：`if len(actual) != len(expected): return math.inf`。

## 不用改，但值得知道

- **锚点上限**（实测突发速率 + 推算）：寄存器内循环的张量核心 FP16 约 107 TFLOP/s，普通 FP32 约 29 TFLOP/s（不含内存访问，GPU 当时与其他代理共用）。
  - 按 README 的 GFLOP 和基线用时，p04、p05、p06、p24 这类矩阵乘主导的输入，理论天花板 $s\approx13$–$14$，到不了 16，所以整题 100 分不可达。
  - 算上取数，实际可能只有一半左右（$s\approx5$–$7$，约 53–65 分，属粗估）；只用 FP32 的解在 p06 上封顶约 $s=3.4$（约 40 分）。
  - 这和“越接近极限越值钱”不矛盾，等实测再调。
- **FP16 与容差**（模拟，`tol_sim.py`、`sample_verify.py`）：所有乘积的输入都舍入到 FP16、累加保持 FP32 时，最坏误差与容差之比在 $L=2$–$4$ 时为 0.26–0.46，$L=16$ 时 0.63，$L=32$ 时 1.085（模拟规模仅 $N=16384$，隐藏输入的元素数还要多三个数量级）。也就是浅层可以用，深层纯 FP16 会超容差。容差不算太松也不算太严，不用改。
- **基线单次提交时长**（推算）：`reference_solution.cu:18` 的注释写“约四分之一秒”，但 p10–p12 按 README 吞吐算每次约 0.74–0.82 秒。离 2 秒还有约 2.5 倍余量，不用动；只有实测看到基线不稳时，再把 `LAUNCH_FMA` 调到 `1e12`。
