# 《操作系统嵌套》难度判断

**结论：这批作品的主体完成度确实高，但“接近全功能优秀”被高估了。现题能区分 Opus 与 Haiku，对前四名尤其前三名的区分不足；作为面向强模型、预期做不完的 100 分钟设计题，难度上限不够。建议先修评分验证，再增加资源竞争、递归嵌套或有因果状态的图形任务，不优先缩短限时。**

- **真实完成度高是主因之一。** 前四件都有实际解释器、消息队列、内层驱动的图形、数据订阅和可续行快照，不能归为“桌面套壳”。Opus 的 98.8 有很强依据。
- **评分饱和是另一主因。** Sol 评分员给前四件的核心机制分别 **69.8、70、70、69.8 / 70**，总分仅相差 1.5；其中有已由源码和另一评分员实测指出的功能缺口。Claude 评分员也混入了题面未要求的偏好性扣分，不能简单改成全部采用 Claude 分数。
- **时间有余量，但没有普遍提前做完的证据。** 主体骨架早出现，关键修复持续到第 90–99 分钟；Haiku 的剩余时间利用明显失效。缩时可能放大启动、安装和检查速度差异，不能替代更深的设计要求。

现合成分前三名只差 **4.6 分**，前四名差 9.7 分，全体差 16.4 分。在本题权重 15% 下，前三名对总成绩的贡献只差 **0.69 分**。五个样本足以指出本批次的饱和，不能据此预测修改后必然出现何种分布。

## 高分究竟从哪里来

**题目自身：实现路线宽、状态规模小。** 自定义程序格式、宿主绘制、同进程隔离、逻辑工作量都允许；这合理地避免了真硬件 OS 的无关负担，也使“可序列化状态机 + 两套桌面 + 自制语言”成为可快速完成的共同路线。整个状态在同一 JS 事件循环内同步复制，快照的一致时点和重复执行大幅简化；这是合法实现，不应事后把“没用虚拟机/多系统进程”当缺陷。固定双层、固定十秒动画、小矩形选区又限制了开放设计空间。

**评分分项：不是单纯太粗，而是同项内关键语义被大量完成项稀释。** 已有 31 个分项、70 分核心机制，继续机械拆得更细价值有限。真浏览器只占 3 分，错写下一格的表格也只占 3 分；Haiku 未建立复制显示边界仍拿显示项一半以上，分叉破坏原连接也可被文件独立与能导出抵消。这样宽泛完成可以积出高分。反过来，现有五项快照要求高度依赖同一个完整状态序列化设计，16 分往往一起拿到；不能据此推断有四项独立高难能力。

**评分员：覆盖与质量尺度两种差异都存在。** Sonnet 的浏览器、表格，Haiku 的 SVG、分叉是可核查的遗漏；Terra/Sol 的若干 0.1–0.5 分差则是“功能有即满”与“实现质量也分层”的系统性差异。Sol 给前四件各 26–27 个分项满分；Claude 给 Sonnet/Sol/Terra 的满分项只有 1/2/0 个。后者也有缺少题面依据的扣分，统一口径应围绕可观察语义，不是整体压分。

**应先改评分执行，不必在题面新增长清单：** 对两位评分员使用相同的短场景：连续键入并 Enter/失焦；网页真实打开新页；两个源 SVG 后隐藏第一个；保持原订阅活跃时分叉并断开分叉；极低承载额度混跑计算/图形。场景按当前分项归属评价，不重复计同一缺陷；自带测试作为辅助证据，不能替代这些外部操作。对仅有源码支持、未实际验证的结论保留证据限制；对语言风格、路径输入方式、速率档数等未写要求不另设偏好。

## 可独立换入的高难要求（按预期区分贡献排序）

以下是候选方向及建议权重，**不是在现有 100 分上追加分数，也不要求捆绑采用**。题面仍保留双层桌面、外层日常应用、内层图形与数据、紫黄 24 号直升机；原有要求继续成立。新分项只评价新增语义，现有消息/投送/快照的通用问题仍归原项。

### 1. 共享预算下的实际资源竞争（建议 20 分）

**可放入题面的需求：**

> 各系统在每个逻辑步内共享有限的执行预算，普通程序、应用服务和子系统承载进程共同竞争。子系统的全部工作受父层实际拨付约束，时间倍率不增加执行预算。文件处理、数据计算和图形取样的逻辑工作量随处理规模变化；未完成工作能在以后取得额度时续行。降低总预算后，各可运行进程仍持续取得执行机会，工作量、完成结果与任务管理器读数一致。

**为什么能拉开：** Haiku 用 afterStep 逐实例驱动，Sonnet 的 native runner 在 VM 预算之外，Sol 外层分别给每个进程额度，Terra 图表/场景整批工作计为一步；Opus 已有较深预算设计，却仍先执行大系统调用再计费。这一要求会同时考到五件的不同薄弱处，不能仅给进程表加一列数字。

**简要评分：** 共享资源预算｜20 分｜不同规模的计算、服务与子系统工作共同受预算限制，能分步续行并获得持续执行机会。

**评分员验证：** 固定逻辑步，混跑长循环、较大数据图表和多轨动画；限制总预算及单个承载预算，比较实际完成工作与记账；改变数据/轨道规模，检查是否仍“一次调用整批做完只算一步”。只验证逻辑预算，不测帧率、吞吐或机器性能。

### 2. 系统实例可递归组成树（建议 18 分）

**可放入题面的需求：**

> 系统中的系统也能创建子系统，支持至少四层桌面与同层多个实例。每层都能管理直属子系统；各实例具有独立的程序、时间、消息、文件和桌面。暂停或停止一个实例时，其后代遵循祖先的运行状态，兄弟子树继续可用；操作、文件传递与窗口归属在嵌套移动、缩放和遮挡后仍指向正确实例。

**为什么能拉开：** 当前五件都把实例管理集中在外层、内层主要是图形工具。Sonnet 的 `outer/system.js` 独占 `instances`/`MessageChannel` 管理，Terra 的 `desktop()` 按 `id==='outer'` 选择两套应用，Haiku 的类也分成 OuterSystem/InnerSystem；Opus 虽共用内核，管理仍在 outer.js。通用内核与写死双层将出现真实改造差距；增加同层实例数量本身没有这种效果。

**简要评分：** 递归系统组织｜18 分｜多层多分支系统能由各自父层管理，祖先运行状态、实例隔离和嵌套操作归属正确。

**评分员验证：** 创建四层及两条兄弟分支，在不同层启动同名程序/文件；暂停中间节点、操作兄弟分支，再恢复和停止该节点。移动缩放多层桌面后拖放文件和编辑文本。此项评价系统组织与归属，预算公平性仍只归方向 1；现有快照分项评价恢复，不在此重复计分。

### 3. 有输入因果的直升机场景（建议 16 分）

**可放入题面的需求：**

> 保留默认十秒的起飞、飞行、失控、撞击与余波演出，并提供可交互的飞行排演。排演中可以改变风、目标航向和故障触发时机；机体、旋翼、影子、落点、损坏与碎片根据已经发生的状态和输入连续变化。排演记录可以保存、打开和跳转回放；从同一记录位置继续给出不同输入，应产生各自连续的后续过程。图形仍由内层协作进程生成，默认演出和交互排演使用同一套场景资源。

**为什么能拉开：** Opus 的 `sampleRole()` 明确只由时间取样，Terra 的烟尘/碎片时刻写死在 `scene()`，Sol 的 motion 资源和 Sonnet/Haiku 的资源也以预定时间轨迹为主。现在“任意跳转 + 快照”可大量依赖纯函数重取样；新要求需要设计输入、历史状态与图形的因果关系。它同时保住最有辨识度的直升机主题，避免只增加桌面杂项。

**简要评分：** 交互场景与回放｜16 分｜飞行输入连续影响场景结果，记录可跳转回放并从同一位置演化出不同后续。

**评分员验证：** 相同起点在不同飞行时刻改变风/航向/故障，比较落点与部件结果；保存后重开并回跳，核对同一记录位置，再分别施加不同输入。只要求因果一致与图形连续，不要求科研级飞行动力学。该项评价排演记录；操作系统快照、SVG 美术和投送正确性仍各归原项。

### 4. 图表向工作簿提交编辑（建议 14 分）

**可放入题面的需求：**

> 图表工作台除接收更新外，还能在图中或数值控件中修改可写数据点，向源工作簿提交一次编辑，并在源完成重算后显示确认结果。公式单元格保留公式，不能作为普通值覆盖。源版本在编辑期间变化时，用户能看到冲突并决定放弃或基于当前值重新编辑；多个图表可以同时连接同一工作簿。一次确认只形成一次源编辑，撤销重做通过工作簿作用于所有相关图表，取消与冲突不产生部分写入。

**为什么能拉开：** 五件目前都主要是单向完整矩阵订阅，选点/改类型不写回源。Sonnet 已在本地 Enter/blur 时重复写下一格，Terra 首字符被选中，Sol 连续输入失焦，Haiku 则外层直接改内层配置；这些实际短板说明“输入 → 一次提交 → 版本确认”的设计尚不稳。写回要求增加真实交互事务，不能靠再画一种图表拿分。

**简要评分：** 图表编辑与一致提交｜14 分｜图表编辑按源版本确认并保持公式、冲突、撤销重做及多图表结果一致。

**评分员验证：** 两图连接同一表，修改普通值和尝试修改公式结果；图中编辑尚未确认时在外层改源，再确认/取消；检查公式、源撤销记录与两个图表，只出现已确认的一次编辑。此项仅评价反向编辑，一致版本的单向发布仍归原数据分项。

**实施顺序：** 先按上述共同场景复核现有评分；若只改一处题目，优先方向 1；若希望明显扩大设计空间，再加方向 2 或 3。不要只把现有快照、投送条款写得更长，也不要只增加更多小组件。新题第一节仍写目标总览，以上具体语义放需求章节；评分只保留各项、分值和一句话打分点，验证步骤留在评分指南中。
